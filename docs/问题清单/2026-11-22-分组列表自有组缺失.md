# 分组列表自有组缺失问题清单 —— 2026-11-22

- **来源**：用户人工反馈 1 项（"客户端的分组界面如果用户已经登录了，那么显示的应该是该账号创建的分组以及当前设备加入的分组。现在仅显示了当前设备加入的分组，账号创建的分组没有显示"）
- **根因**：0x42 分组列表（`GroupService.HandleGroupListAsync`，M2-27 定案"本设备已加入分组全量"）只查 `m.DeviceId == session.DeviceId && m.Approved` 成员行——分组虽**属于账号**（PRD 05 决策 D8），列表却按**设备维度**过滤：同账号第二台设备（登录同一账号但未加入某组）看不到账号创建的分组，创建设备离线/退出该组后更是全员不可管理（审批/邀请码/成员/编辑/解散入口全部缺席）。

## 1. 影响面

| # | 位置 | 问题 | 处置 |
|---|---|---|---|
| 1 | 服务端 `GroupService.HandleGroupListAsync`（0x42） | 已登录会话仅返回本设备成员行对应的分组——账号自有分组缺席 | ✅ 查询并入 `g.OwnerUserId == session.OwnerUserId` 自有分支（未登录分支恒假，行为不变）——与 0x40 `VisibleDevices`"本账号 ∪ 共同分组"同构 |
| 2 | 客户端 `GET /api/groups`（GroupsApi）聚合待审批 | 数据源为 0x42，自有组不返回 ⇒ 待审批申请聚合不到这些组 | ✅ 零改动自愈——服务端并入后 `foreach (IsOwner)` 自动覆盖新增自有组 |
| 3 | 前端分组页（Groups.vue / SimpleGroups.vue） | 账号创建的分组不显示，所有者操作不可达 | ✅ 零改动自愈——`isOwner=true` 行自动获得审批/邀请码/成员/编辑/解散全套操作（均不依赖本设备在组内） |
| 4 | 文档口径 | M2-27 定案"0x42 = 本设备已加入分组全量"与"分组属于账号"（D8）存在维度错位 | ✅ PRD 05 §1 补**分组列表口径**（v0.20）；设计 02 §2.4 0x42 行 / 04 §2.4 / 05 §2 / 06 §2 同步（v1.91）；手册 §5.2（v1.12） |

## 2. 修复要点

- 唯一代码改动点 `src/P2P.Server/Services/GroupService.cs`：0x42 查询从"成员行 join"改写为"groups 表直查 + WHERE 自有 ∨ 成员行"两分支；成员数统计与 isOwner 投影不动（未加入自有组的成员数如实不含本设备）。
- 协议形状零变更（`GroupListItem` 五字段不动）——客户端/前端/api.d.ts/mock 零改动；角色列"所有者"语义如实（不区分本设备是否已加入该组，加入可走凭码入组既有入口）。
- **已知展示局限**（如实记录不扩）：未加入自有组的「成员」弹窗数据源为 0x40 可见设备（本账号 ∪ 共同分组）——本设备与组内跨账号成员无共同分组，弹窗仅列本账号已加入该组的设备；0x40 既有口径，与本次修复正交。

1. 服务端升级（归用户/运维）：过滤在服务端执行，升级服务端二进制即生效——**客户端二进制无需升级**（协议零变更，各端分组页随 0x42 数据自动收敛）。
