## 1. S1 根因链（用户报障①的日志+代码双证据）

同型断网、两种现场形态的对比是定位关键：

- **11-09 01:26（快失败形态）**：路由不可达 → `ConnectAsync` 秒抛 `SocketException`（"套接字操作尝试一个无法连接的主机"）→ 被 RunLoop 捕获、记日志"连接 xxx 失败"、退避 2s 重试 ×12 → 网络恢复后即恢复。**重连循环本身正常**。
- **11-12 13:26（黑洞形态）**：路由器断电但本机网卡链路仍在 → 路由表未撤、SYN 发出后无任何回应 → 自建 5s `connectCts` 超时 → `ConnectAsync` 抛 `OperationCanceledException`（TaskCanceledException 派生）→ RunLoop 过滤条件 `when (e is not OperationCanceledException)` **不捕获**（本意只放行停机，实际把自超时也放行了）→ OCE 穿透 foreach、穿透 while、穿透 RunLoopAsync → 循环任务死亡。现场：13:26:40 后 [control] 仅剩 [report] 每 30s 报"控制连接未就绪（Connecting）"，直至 20:06 重启。

附带说明为何现象是"整个程序瘫"而非仅控制通道：`ClientRuntime.RunRegisteredPathAsync` 的 `while (State != Established)` 等待与打洞/映射恢复全部依赖控制通道就绪，循环死亡后状态永滞 Connecting，映射断链后也无法重打（0x70 无通道可发）。

同族缺陷此前已在 RelayClient 修过一次（M2-38：JOIN 内部超时 OCE 视同承载不可用转 UDP 兜底，2026-10-24 公网实证）——本次是把同一修复模式补到 ControlClient 的连接/握手路径。

## 3. 待批复项（复杂/影响较大，用户判断后处理）

### 3.1 控制通道心跳 Ack 缺失检测（S5）

- **现状**：客户端 0x30 只发不检测应答缺失；NAT 静默丢流（映射表过期、无 RST）时依赖 TCP 重传超时（Windows 默认约 21s~2min）才断线重连，期间状态显示 Established。
- **建议方案**：连续 3 次心跳未收 Ack（±90s）主动断链进重连——与 TunnelSession KEEPALIVE（20s×3 次）同款语义上移到控制通道。
- **影响面**：ControlClient 心跳循环语义改动；需配服务端心跳实际回 Ack 频率核参（当前 0x30 Ack 每跳必回，无服务端改动）；红绿用例需注入静默对端。改动集中、风险低，但属行为语义变化，列待批复。

### 3.2 UDP 承载可靠化（S6）

已有完整设计文档（11-UDP承载可靠化KCP设计.md，v0.1 草案·待评审，7 项决策点）——本报告不重复立项，按该文档评审节奏推进即可。中继场景 TCP 优先已规避主体（M2-38）。

### 3.3 ResolveStunEndpoint 异步化（S7）

启动路径 `Dns.GetHostAddressesAsync(...).GetAwaiter().GetResult()` 改异步并加超时（建议 3s）。改动小但触碰 AttachPuncher 装配路径与测试缝，收益=DNS 挂起时启动不再阻塞数秒，列低优先级待批复。

## 4. 已实施修复明细

### 4.1 修 A：ControlClient 连接/握手全程有界 + 重连循环不可杀（S1 根因，`ControlClient.cs`）

1. **自超时 OCE → 普通异常转换层**：`ConnectAndHandshakeAsync` 包装为转换层，`catch (OperationCanceledException) when (!ct.IsCancellationRequested)` 转 `ControlClientException("连接/握手 xxx 超时（连接 5s + 握手 10s）")`——RunLoop 视为本地址失败，换下一个地址/退避重试；仅停机（ct）OCE 原样传播。
2. **握手段超时**：核心握手流程改用分阶段 deadline（连接段 `ConnectTimeout` 5s；TCP 连上后 `CancelAfter` 重定表为握手段 `RequestTimeout` 10s），Hello/HelloAck/Proof/ProofAck/版本拒答信息获取全部纳入有界等待——消除"TCP 连上但对端不答 → 永久滞留 Handshaking"。
3. **循环不可杀兜底**：RunLoop 整个迭代体包裹 try/catch——内层每地址尝试/会话运行仅 `ct.IsCancellationRequested` 的 OCE 上抛（唯一正常出口），其余一切异常（含未来引入的意外 OCE 泄漏）记日志"重连循环异常（已忽略，继续退避重试）"后继续退避循环。**任何未预期异常从此无法杀死重连循环**。

### 4.2 修 B：TunnelSession 接收循环单帧异常防护（S3，`TunnelSession.cs`）

已认证帧分发 switch 抽为 `HandleDecryptedFrameAsync`，循环内 try/catch：单帧处理异常（handler 异常/反序列化失败等）记日志"帧 0xXX 处理异常（丢弃该帧）"后**丢弃该帧继续收发**——与既有"未知帧容忍丢弃（02 §7）"同口径；不再出现"一帧炸掉整个接收循环→僵尸会话→60s+ 全 channel 冻结→断链重建"。握手期帧丢弃语义不变（THello 重发容忍既有）。
