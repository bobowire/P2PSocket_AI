# 05 · 关键模块设计

> 所属文档集：[README](README.md)　本文给出各核心模块的内部结构与关键算法，接口签名用 C# 表意，实现以本文为准。

## 0. 并发模型总纲（TD-14，统领本文全部模块）

跨组件并发单元固定为下表四类 Actor + 纯 I/O 循环，任何新模块先对号入座再谈实现：

| 组件 | 并发单元 | 说明 |
|---|---|---|
| MappingStateMachine | **全局单 Actor**（`Channel<Event>` 单消费，事件总线投递） | 全部映射状态迁移串行化（§2.1） |
| TunnelSession | **每隧道单 Actor** | 收包循环解析后投递，channel 分发不在 I/O 线程做（§4） |
| ControlSession | **每连接串行** | Pipelines 读循环 → 分发器，已有 02 §2.1 |
| PunchScheduler | **全局单 Actor** | 串行打洞队列（§3.1，OQ-11） |
| socket I/O 循环 | 纯 async I/O，**不执行业务逻辑** | 解析完即投递对应 Actor，I/O 线程不碰共享状态 |

六条纪律：

1. 跨组件共享可变状态**仅限三处白名单**：`DeviceRegistry`、`RelaySessionTable`（均为 ConcurrentDictionary）、统计计数器（Interlocked）；其余一律封装进 Actor 或以不可变快照传递；
2. **禁止新增 `lock`**；需要复合原子操作时改为进 Actor 队列，或用不可变快照替换共享引用；
3. 事件总线（§9）每消费者独立有界 Channel（容量 1024）：**状态类事件**写满即背压等待（生产者 await），**统计类事件**写满即丢弃并计数；
4. `state.json` / `peers.json` 单写入者 + 临时文件原子替换（03 §5）；
5. 优雅停机顺序（不可颠倒）：PunchScheduler 停止入队 → MappingStateMachine 排空 → 隧道排水关闭（NET-75）→ 控制通道最后关闭（保证 0x64 补报统计发出，02 §2.4）；
6. 违反上述任何一条，须在代码注释与本文档同时注明理由。

## 1. 虚拟网卡模块（P2P.Nic，FR-C-201~204）

### 1.1 设计要点

虚拟网卡在本产品中**只承担"提供独立本地监听地址"**（TD-06）：目的地址 = 虚拟 IP 的连接由 OS 本地交付给绑定在该 IP 上的监听 socket，**不进入网卡数据通道**，因此模块不处理任何收发包。

```
interface INicManager
{
    Task<NicHandle> EnsureAsync(IPAddress virtualIp);   // 创建或复用 + 应用 IP（幂等，启动/自愈共用）
    Task RemoveAsync();                                  // 卸载清理（FR-C-203）
    event Action<string>? Degraded;                      // 异常告警 → 本地 Web 展示（FR-C-204）
}
```

### 1.2 Windows（Wintun）

- `Wintun.dll` 随安装包分发至程序目录，P/Invoke：`WintunCreateAdapter(name="P2P-Tun", tunnelType)` / `WintunOpenAdapter`（复用）；
- 创建后调用 `WintunStartSession(最小 ring)` **保持会话开启以维持适配器 up 状态**（不读写 ring）；
- 配置 IP：IP Helper API（`CreateUnicastIpAddressEntry` + `SetIpInterfaceEntry` 设置 on-link 前缀），不依赖 `netsh` 子进程；
- 自愈（FR-C-202）：后台 30s 检测适配器存在性与 IP 绑定，丢失则重建。
- 驱动适配器随卸载删除（`WintunDeleteAdapter` + 删除程序目录 dll）。

### 1.3 Linux（TUN）

- `open("/dev/net/tun")` + `ioctl(TUNSETIFF, IFF_TUN|IFF_NO_PI)`，接口名 `p2p-tun`；
- 配置 IP：优先 rtnetlink（无外部依赖）；M1 允许降级 `ip addr add`（检测 ip 命令存在）；
- 持有 fd 保持接口 up；进程退出自动关闭（systemd 服务重启后重新 EnsureAsync）。

### 1.4 冲突检测（FR-C-204）

启动时枚举本机全部单播地址与路由，若与虚拟网段（默认 100.64.0.0/24）相交，本地 Web 顶部持续告警并建议管理员在服务端调整网段。

## 2. 映射引擎（FR-C-301~307）

### 2.1 结构

```
MappingEngine
 ├─ MappingListener[]        // 每条启用映射一个：TcpListener.Bind(virtualIp:localPort)
 ├─ ChannelManager           // channel 生命周期（对隧道）
 └─ 状态机 MappingStateMachine（PRD 06 §5）：
      disabled → punching → direct / relay / failed
      任意态 → invalid（授权失效事件）
```

> relay 态进入条件 = 设备对打洞失败 **且** 访问方对该目标设备的设备级回退配置开启（D3 v0.4/OQ-10，本地 peers.json）；未开启 → 该设备对全部映射 failed。

### 2.2 数据路径（TCP 映射）

```
本地应用 ──TCP──▶ virtualIp:localPort (accept)
   │ Socket s1
   ├─ 分配 channelId → 隧道发 OPEN{tcp, targetAddr, targetPort}
   └─ 双向 splice（Pipelines）：
        s1 → 读循环 → DATA(channelId) → 隧道发送
        隧道收到 DATA(channelId) → 写循环 → s1
对端收到 OPEN → 连接 target(targetAddr:targetPort)
   成功 → OPEN_OK → 进入 splice；失败 → OPEN_FAIL{reason} → 本地关闭 s1
```

### 2.3 背压（M1 简化 → M2 信用）

- M1：每 channel 发送队列上限 256 KiB，满则暂停读本地 socket（TCP 窗口自然反压对端应用）；
- M2：WINDOW 信用帧（02 §4.2 type 0x0A，v1.8 帧值勘误后——05 本行 0x09 为勘误前旧值，随 M2-05 一并修正），每 channel 独立窗口（默认 64 KiB，`CreditWindow` 账本），按消费回报（载荷 = 已消费字节数，channelId 在帧头）。

### 2.4 UDP 映射（M2，FR-C-303，TD-15）

UDP 无连接，channel 语义定义为**本地应用端点（应用 ip:port）**——映射的目标地址固定（D15），流的区分维度只剩应用端点，与 TCP channel（一条 accepted 连接）语义对称。生命周期：

- **监听**：`UdpClient.Bind(virtualIp:localPort)`；
- **创建**：某应用端点首包到达 → 分配 channelId → 隧道发 `OPEN{udp, targetAddr, targetPort}` 后**乐观直发** UDP_DGRAM（不等 OPEN_OK——UDP 语义下握手往返徒增首包延迟）；OPEN_FAIL 异步到达 → 后续该端点包静默丢弃、映射状态标 failed；
- **服务侧**：每 channel 一个本地 `UdpClient`（源端口随机，目标服务凭四元组区分流），内网目标同样执行 L3 白名单校验（同 TCP，SEC-52 双保险）；
- **路由**：双向均查 channel 表——访问侧 channel ↔ 应用端点，服务侧 channel ↔ 本地 socket，无跨 channel 串流；
- **回收**：双向空闲 60s（可配）→ CLOSE → 双端表项与 socket 释放；同端点再发包 → 建新 channel。已知语义副作用：目标侧看到的源端口会变，DNS 等无状态协议无感，依赖源端口粘滞的协议可通过调大空闲超时缓解；
- **上限**：每 UDP 映射并发 channel ≤ 256（默认，可配；防 DNS 风暴型放大），超出丢弃 + 计数告警（04 §3.2）。

### 2.5 目标地址解析（D15）

`targetAddr == "self"` → 对端连接 `127.0.0.1:targetPort`；否则为对端开放网段内 IP → 对端连接前本地校验 `lan_segments` 白名单（双保险：服务端 L3 校验 + 对端执行点校验，SEC-52）。

## 3. Puncher · 打洞器（FR-C-401~404，02 §5）

```
class Puncher
{
    // UDP：STUN 探测 → 双向发包（打洞包=PTP THello1）
    Task<PunchResult> UdpPunchAsync(PunchContext ctx, CancellationToken ct);
    // TCP：端口预测法（N 条并发，目标端口 = peerStunPort + (N−1)）
    Task<PunchResult> TcpPunchAsync(PunchContext ctx, int concurrencyN, CancellationToken ct);
}
record PunchContext(Guid SessionId, IPEndPoint PeerUdpEp, IPEndPoint PeerTcpEp,
                    byte[] PeerStaticPubKey, bool RelayAllowed);
```

`RelayAllowed` = 访问方本地 peers.json 的设备级回退配置 **AND** 服务端 PunchInvite.relayAllowed（中继全局开关），由 Puncher 出队执行时合成。

关键实现约定：

- **UDP（OQ-18 两段式下的两个角色）**：**访问方**——出队后即时 STUN 探测、端点随 0x70 上送，收到 0x70 Ack（携带对端端点）后立即对 peer 端点连发 THello1（10ms 间隔 ×20）；**被邀请方**——收到 0x71 PunchInvite → 即时 STUN 探测 → 0x76 上报端点 → 不等中转、立即对发起方端点连发 THello1；任一方向握手完成即成功；
- **TCP（双方对称执行，缺一不可）**：先在本地 STUN 探测端口 L 上 `listen(SO_REUSEADDR)`，再并发 N 条 connect：目标统一为 `peerTcpEp.Port + (N−1)`，第 1 条源端口沿用 L、其余 N−1 条用系统分配的不同本地端口（避免重复四元组，机理见 02 §5.2 实现备注）；connect 成功（含 simultaneous open 完成）与 accept 到达**任一先到者**立即执行 PTP 握手，握手完成方胜出并取消其余任务；
- 偏移量集中定义 `static int[] Offsets(int n) => [n - 1];`——保留多偏移扩展点（PRD OQ-1 决议的演进空间）；N 以 PunchInvite 下发值为准（取发起方配置——发起方经 0x70.punchConcurrency 上送、服务端校验 1~5 后回填下发，OQ-19/TD-20，双方同一 N，见 02 §5.2）；
- 失败判定：10s 超时（可配）；结果经 0x72 上报（FR-C-404）；
- 哑节点同样运行 Puncher（被动响应 PunchInvite，FR-C-403），只是不主动调用。

### 3.1 PunchScheduler · 串行打洞队列（OQ-11）

```
PunchScheduler（客户端全局单例，FIFO 串行队列）
 ├─ 入队：映射 enable / 隧道重建 / 中继回切重试 等全部打洞需求（设备对去重：同对已在队列则合并）
 ├─ 出队才执行 STUN 探测 + 打洞；上一会话 完成/超时(10s) 后才处理下一个
 │  ——多目标并发打洞会交叉消耗本端 NAT 的顺序端口分配，污染 +(N−1) 预测基准
 │  （打洞包与 STUN 探测同经本端 NAT，串行化保证预测基准连续）
 └─ 队列深度与当前会话进度暴露给本地 Web 诊断页（06 §3 /api/diagnostics）
```

被邀请方（哑节点/服务方）不排队本地队列，但受服务端侧约束（§5）：同一目标设备至多一个活跃打洞会话；其响应路径 = 收 0x71 → 即时 STUN 探测 → 0x76 端点上报 → 立即对发起方端点发包（02 §5.1③，OQ-18）。

## 4. TunnelHost · 隧道宿主（SEC-11~14，02 §4）

```
TunnelHost
 ├─ Dictionary<peerDeviceId, TunnelSession>   # 设备对粒度：一对设备一条隧道（02 §4.5）
 ├─ 路径管理：Primary(直连 UDP/TCP) + Fallback(中继) 双 socket 并存（切换期）
 └─ 密钥管理：TTL 定时器 → REKEY（排水切换，NET-75）

TunnelSession
 ├─ SendKey/RecvKey（AesGcm 实例化封装，counter 单调）
 ├─ ChannelTable（channelId → 本地 socket 绑定）
 ├─ 接收循环：解帧 → 防重放检查（counter 窗口）→ 分发 channel
 └─ Keepalive 20s + 断链检测（3 次未响应判定断开 → 状态机回 punching）
```

- 加密实现集中在 `Core/Crypto`：`AesGcm`（.NET 内置）、`ECDiffieHellman P-256`、`HKDF-SHA256`、`HMACSHA256`（07 §2）；
- 中继路径：同一 TunnelSession 的帧发往 relay 地址（外层 8B 头由 RelayClient 附加），解帧逻辑不变——**加密与路径解耦**。

实现注记（M2-18 落地）：

- **回退链内联 Puncher**：打洞 Ack 后失败且回退资格真（05 §3.1 合成）→ 0x74（打洞 sessionId 须在服务端台账
  120s 窗内——恰为"仅 Ack 后失败"的语义根源）→ JOIN **先 UDP 后 TCP** 承载兜底（服务端按端独立转发，
  两端承载可异构，02 §6.2 TCP 用于 UDP 被封场景 FR-S-704）→ **PTP 握手即经中继**（THello1 200ms 周期
  重发覆盖对端 JOIN 就绪窗——relay 无缓冲，对端未 JOIN 期间包丢弃）。回退预算独立计量（打洞超时已耗尽
  原令牌）；回退失败并入打洞失败原因 → 映射 failed。
- **被邀请侧关联机制**：RelayGrant 不含对端身份信息（02 §6.1② 仅 relaySessionId+端点）——被邀请侧以
  THello1 载荷首 16B 的**打洞 sessionId** 关联本地预记的邀请上下文（对端 deviceId+静态公钥；服务端合成
  relayAllowed 真才预记、应答成功即撤销、TTL 120s 对齐服务端台账；先记后应答，防 Grant 与打洞应答并发
  到达的竞态）→ AcceptAsync 应答握手 → 会话入宿主。
- **承载标记与状态机**：TunnelSession 以 `ViaRelay`（传输实现类型判定）暴露承载路径——映射引擎据此分派
  relay/direct 态、隧道复用检查（relay 会话上的新映射直达 relay 态，02 §4.5 复用期不重新竞争）、
  direct/relay 态断链均回 punching 重竞争。

实现注记（M2-19 落地，回切直连 OQ-7/NET-75）：

- **0x73 只做协调触发**：访问方（会话发起侧 IsInitiator——防双端同时重打）每 60s（PRD 06 §6；测试缝
  `ClientRuntimeOptions.RelayRetryIntervalOverride`）发 PunchRetry → 服务端台账解析（120s 过期后以
  `RelayService.ResolveActiveRelay` 按分配时记录的 PunchSessionId 反查**活中继**兜底——中继会话存活期
  设备对始终可解析；非发起方/无会话 1001）→ 双端下发 0x73{原 sessionId}（A 侧同族应答=受理回执、
  B 侧推送=重打预备通知）；**实际端点交换与打洞由 A 随后的全新 0x70 两段式驱动**（端点须新鲜，
  不做同会话传输迁移）。客户端 0x73 被 1001 拒（台账与活中继均不在册）→ 退化直接全新 0x70（等效回切）。
- **NET-75 排水切换落在 TunnelHost.Attach**：同设备对新会话挂入即替换——旧会话仍存活（中继↔直连切换）
  走排水窗（默认 2s，`Task.Delay` 后 `Close("replaced_drained")`；窗内接收循环/channel splice 照常，
  在途帧送达）；旧会话已亡（断链后重建场景）立即 Close。会话表即刻指向新会话（后续流量不等排水）。
- **排水期新旧会话并存的一致性**：SessionDisconnected 事件携带会话对象——引擎只清理**旧会话**的
  channel（`e.Session == session` 过滤），新会话 channel 不受旧会话关闭影响；新增 SessionAttached 事件
  驱动无本地打洞结果的 Attach 路径（被邀请方应答/中继被动侧）——直连会话替换中继会话即回切完成，
  relay 态映射翻 direct（明细 `relay_to_direct`）；访问方重打路径经 OnPunchCompleted 携带端点明细
  （Punching/Failed 常规翻牌不变）。
- **服务连续性**：重打洞失败时映射**保持 relay 态**（失败分支只翻 Punching，不碰 relay）——中继承载
  不中断；失败且回退资格真 → Puncher 再走 0x74 **新中继会话**双端整体替换（不做"保留旧中继会话"
  优化——单端丢弃新会话会双端脑裂）。
- **每连接帧连续即满足顺序性**（NET-75 口径）：排水窗内旧路径在途帧送达后才关闭；channel 随旧会话
  关闭而收尾（本地连接 FIN）——断连后未送达的尾部写入不在顺序性语义内，应用侧重连即得新路径。

## 5. 控制服务（服务端，FR-S-101~804）

```
ControlServer（TCP 7000）
 ├─ 每连接 ControlSession：Pipelines 读循环 → 消息分发器（seq/ts 校验 → HMAC 验证 → 处理器）
 ├─ DeviceRegistry：ConcurrentDictionary<deviceId, ControlSession>（在线态、能力模式、最近端点）
 ├─ Authorizer：映射授权判定链 L1~L3（PRD 05 §4 的服务端执行点）
 │     L1 访问方 normal 模式
 │     L2 目标 ∈ 访问方账号设备 ∪ 共同分组设备（SQL 一次查询）
 │     L3 targetAddr=self 放行；否则校验目标设备 lan_segments 覆盖
 └─ SignalingCoordinator：PunchRequest → 校验 → 两段式端点互换协调（OQ-18，02 §5.1）
       第一段：向被邀请方下发 PunchInvite（发起方端点/公钥/N/relayAllowed）
       第二段：收被邀请方 0x76 端点上报 → 向发起方下发 PunchRequest Ack（被邀请方端点）
```

- **打洞会话协调（OQ-11 + OQ-18）**：SignalingCoordinator 维护 per-device 活跃会话约束——同一设备同时至多参与**一个**打洞会话（既作为目标也作为发起方）；并发 PunchRequest 命中同一目标设备时排队下发邀请（PunchRequest 挂起，Ack 延后至轮到——与两段式 Ack 延后语义一致）；同设备对隧道已存活或打洞进行中 → 直接 Ack 返回进行中/已复用，不重复邀请（去重）；被邀请方离线/邀请不可达 → 立即 Error 4005 TARGET_OFFLINE（04 §5），发起方映射直接 failed 不等超时；0x76 在会话超时（10s）内未到达 → 会话按失败收尾；
- 心跳超时 30s → DeviceRegistry 移除 + last_seen_at 落库（FR-S-104）；
- 禁用即时生效（FR-S-105/204）：管理员禁用设备/用户 → 服务端立即关闭对应 ControlSession（踢线）并推送 0x75——设备禁用：该设备会话直接断开；用户禁用：其名下所有在线设备收 `newCapability=passive` 即时降级为哑节点；
- 授权失败写 audit_logs（`punch_deny`/`mapping_deny`，SEC-51）。

## 6. 中继服务（服务端，FR-S-701~704，02 §6）

```
RelayService
 ├─ RelaySessionTable：relaySessionId → { 端A地址, 端B地址, 创建时间, 字节计数 }
 ├─ UDP：单 socket 收发循环（epoll 规模内；百级会话无压力）
 ├─ TCP：每连接一个转发对（仅 u16 分帧转发）
 ├─ 限速（M3）：令牌桶 per-session + 全局（FR-S-703）
 └─ 回收：空闲 90s / 会话任端 KEEPALIVE 停止
```

relay 对帧内容**只剥离外层 8B 会话头**，零解密能力（TD-11）；统计字节量供仪表盘（FR-S-810）。

### 6.1 实现注记（M2-07 落地）

- **端槽认领（地址学习）**：RELAY_JOIN 按源端点认领端槽——已学地址精确匹配（刷新）优先 →
  空槽按控制连接源 IP 偏好 → 先到先得入 A；双端同 IP（回环/CGNAT）时先 JOIN 者入 A。
  槽位仅作地址归属，转发"另一端"与标签无关；两端已满且不匹配的未知源**保守丢弃**（防会话劫持，
  重绑定由空闲回收 + 重新 allocate 兜底）。TCP 重连不支持（idle 回收后重新 allocate 覆盖）。
- **转发承载选择**：对端 TCP 连接在即走 TCP（u16 分帧），次选已学 UDP 地址送裸 datagram；
  均无 = 对端未 JOIN——**无缓冲丢弃**（JOIN 确认后方可收）。UDP→UDP 裸帧 datagram、
  UDP→TCP u16 分帧，混合承载交叉转发。
- **写串行化**：per-end 信号量串行化该端出站帧（UDP 来源与 TCP 来源的转发可能并发写同一流）+
  全局 UDP 发送信号量（多会话共用单 socket）；对端 TCP 已死时写失败仅丢当包、由其读循环触发回收。
- **0x74 对端解析**：SignalingCoordinator 会话台账——打洞会话结束（0x76 完成与超时两路径）
  保留 sessionId → (Initiator, Target) 120s（`RelayLedgerTtl`），仅发起方可申请；错误路径：
  relay_enabled=0 → 5002；台账 miss/非发起方 → 1001 `session_unknown`；对端离线 → 4005。
- **端点派生**：RelayGrant 的 host = 各客户端自己控制连接的**本地侧地址**（LocalEndPoint——
  经哪个接口到达即回哪个地址，多宿主正确）；端口 = relayPorts[0]/UDP、relayPorts[1]/TCP。
  relay_enabled 关闭仅拒绝分配（5002），不停监听端口。
- **回收细节**：空闲按**任端**最后包时计（KEEPALIVE 即业务流量刷新）；TCP 端断连即收会话并
  一并关闭对端连接（"任端 KEEPALIVE 停止"）；TCP 首帧 JOIN 10s 超时防占坑；u16 帧长上限
  16424B（8B 头 + PTP 帧上限），len=0/超限断连（AI-19）。

## 7. STUN 服务（服务端，FR-S-601~603，02 §3）

- UDP：单 socket 循环 `ReceiveFrom → 校验 DEVICE-AUTH → XOR-MAPPED-ADDRESS 回包`；未认证静默丢弃；
- TCP：3478 监听，短事务（收一个 Binding Request 即回即关）；
- 认证校验：HMAC + ts 窗口 + nonce 去重（02 §3.2 内存缓存 5min）；
- 防滥用兜底：未注册 deviceId 的认证必然失败；可配 `stun_auth=0` 仅测试环境关闭（server_config）。

### 7.1 风暴防护（TD-18，分层四道闸）

STUN 是唯一无连接、无握手成本的 UDP 入口，须在 HMAC 计算之前/边缘逐层拦截，越早越便宜：

| 闸 | 位置 | 规则（默认，可配） | 超出动作 |
|---|---|---|---|
| ① 单 IP 令牌桶 | HMAC 之前 | UDP 50 pps / 突发 100；TCP 每 IP 并发连接 ≤ 4 | 直接丢弃 |
| ② 查表先于验签 | HMAC 之前 | deviceId 不在注册表 → 跳过 HMAC 直接丢 | 丢弃（枚举 16B 随机 GUID 不可行，查表时序侧信道可接受） |
| ③ 每设备限速 | 认证通过后 | 10 QPS（正常一次打洞仅 2~4 次 Binding） | 丢弃 |
| ④ 全局熔断 | STUN 端口聚合（UDP 数据报 + TCP 连接到达，秒窗计数） | 总速率超 2000 pps → **5s 熔断**（M2-06 执行口径为单级：原设想的"仅服务在线设备"中间级未实现——闸② 认证后伪造源已被排除、预认证洪泛由 ①④ 覆盖，中间级在 STUN 无连接语境须查控制面在线态，成本高于收益） | 熔断期间客户端由 PunchScheduler 失败路径走中继/重试兜底（§3.1） |

配置键 `stun_rate_per_ip / stun_rate_per_device / stun_circuit_pps`（03 §2.8）；丢弃计数器 `stun_dropped_total{reason=rate|auth|circuit}` 进仪表盘（04 §3.2）。

实现注记（M2-06，随编码定案）：闸序 **④→①→②→③** 逐层先于 HMAC——④ 到达聚合先于一切处理、① 的 TCP 侧为每 IP 并发连接 ≤4（连接级限速天然抗突发，TCP 不另设令牌桶）、UDP 侧令牌桶容量=突发、③ 桶容量=QPS（正常一次打洞仅 2~4 次 Binding）；nonce 去重缓存 UDP/TCP 两路共用（跨运输层重放同被拦截）；TCP 短事务读超时 3s（防慢速连接占住并发额度）；令牌桶以 TimeProvider 计时（测试 FakeTime 推进补币）；`stun_dropped_total` 以进程内计数承载（StunGuard.Snapshot()），仪表盘端点 M3 落地。

### 7.2 NAT 行为发现扩展预留（M3 · RFC5780 子集，2026-09-12 用户指示）

> 结论先行：STUN 版本与打洞成功率无因果关系（Binding 返回的映射端点 3489/5389/5780 等价，成败由双方 NAT mapping × filtering 行为组合决定）；5780 的价值是**判型**——本节为 M3 诊断（FR-C-808 stun-test"NAT 行为初判"）预留技术口径，M2 不实现。

- **协议扩展**：STUN 服务增加**第二监听地址**（不同公网 IP 或同 IP 异端口），Binding 响应增 `OTHER-ADDRESS`（告知辅助地址）与 `RESPONSE-ORIGIN`（实际回包源）两属性（RFC5780）；DEVICE-AUTH 认证口径不变；
- **判型方法**（客户端 stun-test 端点编排，多次 Binding 对比）：
  - mapping behavior：同目标两次探测端口不变 → **EIM**（锥形）；换目标（主↔辅地址）端口变 → **ADM/APDM**（Symmetric 族）；
  - filtering behavior：请求服务器从辅助地址回包，能收 → **EIF**（FullCone）；仅主地址可收 → **ADF/APDF**（Restricted 族）；
  - TCP 变体：同法探测 TCP 映射的分配规律（是否 Address-and-Port-Dependent、外部端口是否顺序递增 → SymmetricSequential 判定，端口预测适用性依据）；
- **用途**：① 诊断页展示本机/对端 NAT 分级；② 打洞前不可穿透组合（如 Symmetric×锥形）预判 → 跳过打洞直走中继（省 10s 超时，属策略优化，M3+ 评估）；③ A-5 端口预测适用性辅助判定；
- **边界**：单公网 IP 部署时辅助地址缺省 → 判型降级为仅 mapping 行为（filtering 不可测），端点如实标注。

## 8. 哑节点模式（客户端，PRD 05 §3）

实现为**能力开关而非独立代码路径**：

| 行为 | normal | passive |
|---|---|---|
| 控制通道（Hello/Proof/心跳/配置上报） | ✓ | ✓ |
| Puncher 被动响应（服务方角色） | ✓ | ✓ |
| 本地 Web 只读状态/开放网段/日志 | ✓ | ✓ |
| 主动类 API（设备列表/分组/映射增删启停/打洞发起） | ✓ | 入口置灰 + API 返回 2002（04 §2） |
| 服务端主动类消息 | ✓ | 拒绝 + 审计（02 §2.5） |

登录/登出（0x21/0x22）即时切换 `ControlSession.Capability` 并广播 `login_state` WS 事件；用户被管理员禁用时经 0x75（`newCapability=passive`）触发同样的即时降级（FR-S-204）。

## 9. 模块间事件总线（进程内）

采用轻量事件聚合（`System.Threading.Channels` 单播 + 内存事件），关键事件：

```
ControlClient.PunchInvited        → Puncher / TunnelHost
Puncher.Completed(result)         → MappingStateMachine
TunnelHost.PathChanged(direct|relay) → MappingStateMachine + Stats
MappingStateMachine.StateChanged  → LocalWebApi(WS 推送) + ControlClient(0x62 上报)
NicManager.Degraded               → LocalWebApi(告警)
```

设计约束：事件处理不允许阻塞发布线程；状态机单线程消费（Actor 化，避免锁）。

## 10. 设备识别码生成（FR-C-104）

注册时的 `macCode`（初始识别码）生成规则：

1. **多网卡选取**（按优先级取第一个命中）：
   ① 排除虚拟/回环网卡（InterfaceType = Tunnel/Loopback；名称匹配 Hyper-V/VirtualBox/VMware/Wintun/Docker 等前缀黑名单，表驱动可扩展）；
   ② 优先"已上线 + 拥有默认网关路由"的物理网卡（路由表比对）；
   ③ 多块并列时取 MAC 字典序最小者（保证结果稳定）；
2. **回退**（容器/极端虚拟化取不到合格 MAC）：机器指纹——Linux `/etc/machine-id`、Windows 注册表 `MachineGuid`，SHA-256 后取前 12 位十六进制充当"MAC"；
3. `macCode = "P2P-" + MAC去冒号大写`；仅注册时使用，注册后权威身份为服务端签发的 deviceId（D6），换网卡不影响既有设备绑定。

单元测试：网卡枚举黑名单表驱动、多网卡排序稳定性、回退指纹路径（09 §2.1）。
