# 02 · 通信协议设计

> 所属文档集：[README](README.md)　编码：MessagePack（TD-05）；多字节整数小端；所有协议版本号 `v1`。

## 1. 协议总览

| 协议 | 承载 | 用途 | 对应 PRD |
|---|---|---|---|
| PCP（P2P Control Protocol） | TCP 7000 长连接 | 注册、鉴权、心跳、设备/分组数据、打洞信令、配置同步 | FR-S-1xx~8xx |
| STUN-R（RFC 5389 子集） | UDP/TCP 3478 | 公网端点探测（带设备认证扩展属性） | FR-S-601/602/603 |
| PTP（P2P Tunnel Protocol） | UDP/TCP（打洞成功路径） | 端到端加密、channel 复用、保活、密钥轮换 | SEC-11~14、NET-7x |
| RLP（Relay Protocol） | UDP/TCP 7010+ | 中继会话接入与密文转发 | FR-S-701~704 |

## 2. PCP · 控制协议

### 2.1 分帧

```
+----------------+----------------------+
| u16 bodyLen    | MessagePack(body)    |
+----------------+----------------------+
bodyLen ≤ 64 KiB；单连接串行处理；TCP NoDelay 开启。
列表类大消息（如 0x40）**必须应用层分页**（OQ-16，见 0x40），禁止依赖超限帧或协议层续传。
```

### 2.2 消息公共头（每个 MessagePack body 首字段）

```
record MsgHeader(
    u32 seq,            // 连接内单调递增
    u64 timestampMs,    // 校准后时钟 ±120s 窗口外被拒（防重放，SEC-22；时钟对齐见 2.3）
    u8  msgType,
    ...payload)
```

每条消息尾部附 `hmac: bytes[32] = HMAC-SHA256(connMacKey, header||payload)`；`connMacKey` 由握手派生（见 2.3）。**未注册设备的首个 `Register` 消息例外**：无连接密钥，不携带 hmac，靠注册准入闸门（开关/单 IP 频控/总量）与 IP 黑名单防滥用（07 §5/§13，SEC-61/73，M5 起）。

### 2.3 连接握手（时序）

```
C → S: Hello { protocolVersion, deviceId?, nonceC }               // 不校验 ts（尚无共享时间基准）
S → C: HelloAck { serverVersion, protocolVersion, nonceS, status, serverTs, loginEphPub?(65B) }
       status = OK | NEED_REGISTER | VERSION_NOT_SUPPORTED(→ 触发升级引导 FR-C-904)
C:    时间对齐（OQ-12）：RTT = t(收到HelloAck) − t(发出Hello)；
       offset = serverTs + RTT/2 − t(收到HelloAck)   // 传输耗时按 RTT 半程补偿
       此后全部消息 timestampMs 以 本地时间 + offset 生成（STUN DEVICE-AUTH 同用此 offset）
C → S: Proof { hmac = HMAC(deviceSecret, nonceC|nonceS) }        // 注册过的设备；ts 校验自此生效
S → C: ProofAck { ok }
       connMacKey = HKDF-SHA256(deviceSecret, nonceC|nonceS|"pcp-mac")
       ts 超窗 → Error 5005 TIME_SKEW{serverTs}，客户端重算 offset 后重试一次
```

- `Hello.protocolVersion` 字段位置与语义**永久冻结**（TD：升级引导依赖，PRD FR-S-804）；
- `loginEphPub`（v1.67/M5，TD-25，SEC-26）：服务端**每连接临时** P-256 公钥（连接关闭即弃），0x20/0x21/0x23 密码字段 ECIES 封装的接收钥（格式与硬切口径见 07 §10）；缺失=旧服务端，客户端拒绝发送登录族、**不回退明文**（OQ-21①）；
- `VERSION_NOT_SUPPORTED` 时服务端仍接受 `UpdateInfoRequest`（见 2.4），随后由客户端主动断开；
- 时钟对齐持续维护：0x30 Ack 的 `serverTs` 周期性重算 offset（跟踪本机时钟漂移；异常跳变时重新握手对齐）。

### 2.5 哑节点约束的执行点（PRD 05 §3）

服务端 `ControlSession` 维护能力模式；**主动类**消息 `0x20/0x21/0x23/0x40/0x42/0x50~0x57/0x60/0x70`（用户与分组管理、列表查询、映射、打洞发起）在 passive 模式下直接回 `Error(FORBIDDEN_PASSIVE)` 并写审计日志（SEC-51）。**本机管理与被动同步类** `0x13/0x14/0x30/0x62/0x63/0x64` 正常受理（PRD 05 §3 矩阵）。

**重连会话语义（2026-10-18 缺陷批次 2 修 D）**：登录绑定（`session.OwnerUserId`）为会话级——每条 TCP 连接一个新 `ControlSession`，随连接生死。断线重连的兜底双轨：①服务端 Proof 握手完成后，同设备旧会话的 `OwnerUserId` **继承**到新会话（登录中闪断→可见性/分组管理自动恢复；登出后旧会话已清 null→新会话默认 null，登出语义不被重连洗白；用户已禁用/删除不继承——继承前查库即时收口，不等 PresenceMonitor 30s 兜底；Capability 不继承，维持新会话初始 normal 口径与客户端镜像一致）；②客户端凭据重放（05 §8，P2 方案 a 的重连对等修复）。不走库恢复——`Device.OwnerUserId` 登出保留在库（下次登录免重绑），从库恢复会把登出洗白成已登录。

## 3. STUN-R · STUN 子集（RFC 5389）

### 3.1 范围

- 仅实现 **Binding Request/Success Response**；不做长期凭据/TURN 扩展；
- 报文头 20B：`type(2) msgLen(2) magicCookie(4)=0x2112A442 transactionId(12)`；
- 响应属性：`XOR-MAPPED-ADDRESS (0x0020)`；请求须携带自定义认证属性；M3-15 起另有 RFC5780 判型三属性（§3.2a，按服务端配置条件携带）。

### 3.2 设备认证扩展属性（FR-S-603）

```
Attribute 0x8020 DEVICE-AUTH:
  deviceId(16B) + nonce(16B) + ts(8B) + HMAC-SHA256(deviceSecret, deviceId|nonce|ts|transactionId)(32B)
```

- 不通过则静默丢弃（UDP）/ 关闭连接（TCP），不回应；
- ts 窗口 ±120s（使用 §2.3 校准 offset），nonce 去重缓存 5 分钟（防重放）。

### 3.2a RFC5780 判型属性（M3-15，FR-C-808 诊断子集）

```
Attribute 0x0003 CHANGE-REQUEST（请求，4B）: flags 大端——changeIP=0x04 / changePort=0x02（任一置位即要求从另一端点回包）
Attribute 0x802B RESPONSE-ORIGIN（响应，8B 明文地址）: [0]=0 保留 + [1]=family 0x01 + port(2B 大端) + addr(4B)
Attribute 0x802C OTHER-ADDRESS（响应，8B 明文地址）: 同上布局——另一监听端点（相对语义：主回包通告辅/辅回包通告主）
```

- 仅服务端配置 `stun_alt_addr`（第二监听，05 §7.2）时携带——未配置时响应与 M1 形状逐字节一致（单地址世界零回归）；
- **HMAC 输入不含属性区**（§3.2 定式）：CHANGE-REQUEST 追加于 DEVICE-AUTH 之后不破坏认证；
- 判型编排与两桶族口径见 05 §7.2 实现注记。

### 3.3 TCP Binding 的使用约定（TCP 打洞数据源）

客户端以**专用本地端口 L** 发起 TCP 到 STUN:3478，完成一次 Binding 事务后**立即关闭**；得到的映射即 `L→L'`。该本地端口 L 随后被用于 TCP 打洞的 listen+connect（见 §5.2）。

## 4. PTP · 隧道协议（端到端加密）

### 4.1 会话密钥握手（打洞成功后立即执行）

双方 static 密钥（P-256）公钥已经服务端 `PunchInvite` 交换（受服务端信任通道保护，SEC-13）。

```
A → B: THello1 { sessionId, ephA(P-256公钥), nonceA }
B → A: THello2 { ephB, nonceB, mac = HMAC(kBS_static共享, hash(THello1||THello2前文)) }
A → B: TConfirm { mac = HMAC(kAS_static共享, hash(全部前文)) }

k_static = ECDH(staticA, staticB)                       # 身份绑定（服务端分发的公钥）
k_sess   = HKDF-SHA256(ikm = ECDH(ephA,ephB) || k_static,
                       salt = sessionId|nonceA|nonceB,
                       info = "ptp-v1",
                       len  = 64)                        # 前32B=发送密钥A→B，后32B=B→A
```

- 双重 ECDH（ephemeral-ephemeral + static-static）：静态部分绑定设备身份防冒充，临时部分提供会话独立性；
- 静态-静态 ECDH 仅用于握手认证，不直接加密业务数据。

### 4.2 帧格式

```
+------+------+-----------+---------+--------+==================+
| ver  | type | channelId | counter | u16len |   AEAD 密文       |
| u8=1 | u8   | u32       | u64     |        |  (含16B GCM tag)  |
+------+------+-----------+---------+--------+==================+
AEAD = AES-256-GCM(key=会话方向密钥, nonce=counter 的12B小端, aad=帧头明文部分)
counter 每方向独立计数、严格递增；收到重复/回退计数即丢弃并告警（防重放，SEC-12）
```

实现注记（M2_38 根因修复，v1.44）：①"严格递增"的发送侧兑现=`SendChannelFrameAsync` 在 `_sendGate` 内完成 counter 分配+密封+写传输（counter 序=线上序）——写若在闸外，多发送方（并发 splice DATA/WINDOW 回报/keepalive）释放闸后的调度/写阻塞可倒置线上到达顺序，倒置深度超接收侧 `ReplayWindow` 容差 64 时按"回退"整帧丢弃=字节流静默缺段+该帧信用永不回报=发送侧永久停滞（中继满载间歇复现实证：counter=441/544/896 三帧丢失即致 8 并发流 30s 挂起）；②接收侧防重放为 64 深度滑动窗（窗内序外到达按迟到接受、窗内重复与出窗回退丢弃）——窗口内小倒置无害，per channel 发送序仍由调用方串行化保证。
实现注记（M6-03 落地，NET-77）：接收侧防重放窗口 64 → **4096**（决议点 ②）——KCP 承载下跨 conv 乱序深度上界 ≈ 每 channel 在途 64KiB 信用 ≈ 48 帧 × channel 数 + conv 0 控制帧，窗口 64 必然不够；4096 按 conv 上限 256 满载仍容 8.5 倍余量（bitmap 512B）。窗口只放宽"旧帧迟达"容忍度，**同 counter 重放拦截与窗口大小无关**（bitmap 命中即拒）——SEC-12 安全语义零变化（07 §9 注记 ⑤）。

| type | 名称 | 说明 |
|---|---|---|
| 0x01 | OPEN | 建 channel：{targetProto, targetAddr, targetPort}（访问方向对端申请打开目标连接） |
| 0x02 | OPEN_OK / OPEN_FAIL | 对端连接目标的结果；FAIL 携带原因码 |
| 0x03 | DATA | 流数据（TCP 映射） |
| 0x04 | CLOSE | 关闭 channel（正常/异常） |
| 0x05 | KEEPALIVE | 20s 周期（NET-72 ≤25s）；对端回 KEEPALIVE |
| 0x06 | PING | RTT 测量请求（本地 Web 诊断页用；v1.8 勘误：PING 与 PONG 为独立帧值） |
| 0x07 | PONG | RTT 测量应答（v1.8 勘误：对齐 M1 实现，原"0x06 PING/PONG 合一"废止） |
| 0x08 | REKEY | 密钥轮换（见 4.4；v1.8 勘误帧值，原 0x07 顺移） |
| 0x09 | UDP_DGRAM | UDP 映射数据报帧 {channelId, payload}（M2，FR-C-303；目标地址已由 OPEN 固定，channel 生命周期见 05 §2.4/TD-15；v1.8 勘误帧值，原 0x08 顺移） |
| 0x0A | WINDOW | channel 流控信用（M2；M1 先用有界缓冲+背压，见 05 §2.3；v1.8 勘误帧值，原 0x09 顺移） |
| 0x0B | FRAG | UDP_DGRAM 分片（M2-20 定案回填，v1.28）：载荷 {dgramId u32, index u16, more bool, chunk bin}；UDP_DGRAM 明文超 1368B（=1400−16 头−16 tag）即按 1352B/片切片为同 channelId 的 FRAG 序列（同一数据报共用 dgramId，more=false 为末片、index 从 0 起→总片数=index+1），接收侧按 channelId+dgramId 攒齐重组为完整数据报交付；分片阈值与承载类型解耦（TCP 承载 UDP_DGRAM 语义不变、同口径分片，02 §6.2） |
| 0x0C | REKEY_ACK | REKEY 应答（M2-21 定案回填，v1.29）：与 REKEY 载荷同构定长 81B {新 eph 公钥 65, 新 nonce 16}；以**旧发送钥**封印（发起方尚未切换）；帧类型合法域上界随之扩至 0x0C（与 OPEN/OPEN_RESULT、PING/PONG 的分立帧值惯例一致） |

### 4.3 复用与背压

- 一条隧道复用设备对之间**全部映射与全部应用连接**的 channel（channelId 由发起侧分配，32bit 随机起点避碰撞；生命周期规则见 §4.5）；
- TCP 直连承载时无 MTU 限制，DATA 上限 16 KiB；UDP 承载时帧 ≤1400B（KCP 承载同口径——KCP 自分段[Mtu 1400/MSS≈1376]，发送侧 1368 分块不变，§4.6；满帧 1400B 超 MSS 拆 2 段 ~1.7% 段开销，接受）；
- 背压：M1 = 同步 splice + 每 channel 有界发送队列（满则暂停读取本地 socket，TCP 自然反压）；M2 = WINDOW 信用机制。
- 混淆扩展点（FR-C-503/SEC-15，P2 不实现）：帧格式外层预留传输包装层——`IObfuscationAdapter`（直通/混淆两种实现），首版直通透传；后续可插入 udp2raw 类伪装而不改动 PTP 帧格式与加密层。

### 4.4 密钥轮换（SEC-14）

- 会话密钥 TTL 默认 3600s（可配）或手动触发；
- 到期由会话发起方发 `REKEY { 新 eph 公钥, nonce }`，对端回 `REKEY_ACK`，按 4.1 相同方式派生新密钥；
- 切换遵循**先排水后切换**（NET-75）：新密钥生效后旧密钥保持接收窗口 2s 排空在途帧，然后销毁；
- 切换次序保证（M2-21 落地，v1.29）：**响应方**接收环先行切换 → 以旧发送钥回 REKEY_ACK → 发送钥再交换（发起方的新代帧即刻可解、其切换前在途旧代帧走排水窗）；**发起方**在接收循环内原子完成"解析 ACK→派生→双钥切换"——处理下一帧前新代接收钥已就位（响应方发 ACK 即换发送钥，紧跟 ACK 的新代帧无竞态窗）。

### 4.5 隧道生命周期与打洞次数（设备对粒度）

| 规则 | 说明 |
|---|---|
| 粒度 | 隧道是**设备对级**资源：A↔B 同一时刻至多一条活跃隧道；全部映射、每条映射的每个本地连接（channel）都复用它，**不按连接/映射分别打洞** |
| 建立 | 首个需要到达对端的映射 enable 且无可用隧道时，发起一次 PunchRequest → 打洞 → PTP 握手 |
| 复用 | 隧道存活期间，任何新映射启用、新应用连接接入，直接在既有隧道上 OPEN 新 channel（无信令、无打洞、无重新握手） |
| 打洞承载选择 | **目标设备级本地配置 punchMode**（TCP/KCP，默认 TCP；NET-78/设计 12 号，M7 上收设备级——映射 proto 字段保留存档、不再决定打洞方式；kcp=UDP 打洞+承载协商 KCP 优先，承载降级 §4.6 M6-04 决议不变）；中继回退后 60s 回切与 Failed 态周期重试（同一循环）以优先模式为起点 **TCP/KCP 交替**——手动重试/映射启用/断链=新序列从头（触发点分类设计 12 §5.4）；0x70 proto 恒执行层口径 tcp/udp 二值（kcp 不上 wire） |
| 承载绑定 | UDP 打洞成功 → UDP 承载；TCP 打洞成功 → TCP 承载；均失败 → 按访问方对**该目标设备的设备级回退配置**（D3 v0.4/OQ-10，客户端本地 peers.json）决定：开启 → 中继（同一 TunnelSession 的备用路径）；未开启 → 该设备对全部映射 failed。后续映射复用当前承载，不重复尝试其他方式（隧道重建时才重新竞争） |
| 重建 | keepalive 连续 3 次无响应 / 底层 socket 故障 → 隧道销毁（新 sessionId、计数器清零）→ 各引用映射状态机回 punching → 重新打洞 |
| 空闲回收 | 无活跃 channel 且无启用中映射 → 空闲 300s（可配）优雅关闭（先排水，NET-75）；下次需要时重新打洞 |
| 中继会话 | RelayAllocate 同样以设备对为粒度（回退与否由设备级配置门控，见上行）；中继态 60s 直连重试成功按"路径切换"处理，不新建隧道 |

设计动机：① 打洞成本高（信令往返 + 每次消耗双方 NAT 的 N 个顺序端口分配，频繁打洞会推远预测基准）；② 一条路径一份 20s 保活；③ 一套会话密钥，REKEY 简单；④ 多映射共享路径、按 channel 计量。

### 4.6 UDP 承载可靠化（KCP 多 conv）（NET-77，11 号 §4/§5/§7，M6 落地）

UDP 打洞直连承载从"裸数据报"升级为**单 socket 上 KCP 多会话（conv）按 PTP channel 分流 + 裸 UDP 旁路**：channel 级可靠有序、channel 间队头隔离、UDP_DGRAM 丢包容忍语义保持；TunnelSession 帧逻辑、加密体系、打洞流程、成功判定零语义变更（TD-29 定案：协议数学 1:1 自研移植 skywind3000/kcp，四参考全 MIT attribution）。

**conv 路由表**（承载层按明文帧头判定，不解密）：

| PTP 帧 | conv | 理由 |
|---|---|---|
| OPEN / KEEPALIVE / PING / PONG / REKEY / REKEY_ACK | **conv 0**（全局控制流） | 接收侧只能从经 AEAD 的 OPEN 学知新 conv（无 lazy accept——安全边界）；双方 conv 0 会话建立即存在 |
| OPEN_RESULT / DATA / CLOSE / WINDOW | **conv=channelId** | channel 内严格有序=字节流语义修复核心；CLOSE 与同 channel DATA 同流（CLOSE 不会越过尾部 DATA 提前交付） |
| UDP_DGRAM / FRAG | **裸旁路** | 丢包容忍语义保持（TD-15）；不被可靠层重传延迟污染 |
| THello1/2/TConfirm | 打洞期裸帧 | 不进 KCP（§5.1 承载切换在握手成功瞬间） |

**魔数 demux**：KCP 包首字节恒 0x4B（后随 conv u32 LE + KCP 段头）→ conv 表命中→端点 Input；未命中丢弃+计数（`kcp_unknown_conv_dropped`，未授权 conv 防线）。非魔数（裸路径）经**白名单闭包**：ParseHeader ver==1 且 type∈{UDP_DGRAM(0x09), FRAG(0x0B)} → 裸接收队列（有界 256，DropOldest+计数）；其余（**迟到 STUN 应答**——首字节 0x01 恰与 PTP ver 同值、type 0x01 形似 OPEN，现状裸承载上曾致整隧道误杀/迟到握手帧/垃圾）→ 丢弃+计数，顺带修复该潜伏缺陷。

**承载切换时序**（§5.1 ⑥）：握手成功瞬间按 caps 判定（§2.4 bearerCaps 四消息字段；两端同式 `kcpEnabled=(myCaps&peerCaps&CAP_KCP)!=0`，开火前完成、无第三态无脑裂；旧服务端 typed 重序列化剥未知字段 → 双端同判 false 一致降级；混布自动降级裸 UDP）→ true: `KcpTunnelTransport.Adopt(socket, pinnedEndpoint)`（socket 所有权移交，`UdpPunchTransport.ReleaseSocket()` 后其释放不关 socket）→ `TunnelSession.FromEstablishedKeys(…, kcpTransport, …)`（M2-16 缝既有）；false: 现状裸路径。承载与会话同生共死（§4.5），中途不可切换。

**会话层接缝**（05 §2.3/§4 注记）：`IKcpConvControl.EnsureChannel/RemoveChannel`——SendOpenAsync 前置 / 接收循环 Open case（鉴权前置）/ OnOpenResult !Ok / OnClose / RemoveChannelCredit 汇聚点，五处幂等；transport 未实现（TCP/中继/裸承载）即 no-op 零回归。ReplayWindow 64→4096（§4.2 注记）。channel conv 上限 256/会话（超限全帧降级 conv 0——保正确性牺牲隔离）。

## 5. 打洞交互（D10 / OQ-1 决议的实现细节）

### 5.1 UDP 打洞

> 打洞调度（OQ-11）：客户端 PunchScheduler 全局**串行队列**（05 §3）——上一会话完成/超时后才执行下一个，避免多目标并发打洞交叉消耗本端 NAT 顺序端口分配、污染 +(N−1) 预测基准；服务端 SignalingCoordinator 同时保证**同一目标设备至多一个活跃打洞会话**（并发申请排队/合并，05 §5）。
> 端点互换（OQ-18，**两段式**）：STUN 映射仅打洞期内瞬时使用（§5.3 不长持），服务端无从预知双方端点，由本轮信令**现场收集互换**——发起方端点随 0x70 上送（第一段），被邀请方端点经 0x76 回传、由 0x70 Ack 送达发起方（第二段）。
> 直连优先（NET-76，v1.63）：同一两段式顺带互换本机直连候选地址并与公网端点路径并行竞赛，见 §5.4。

```
① A（访问方）PunchScheduler 出队 → 即时向 STUN:3478/UDP 发 Binding → 得 A 端点
   → PunchRequest{..., requesterEndpoints}（第一段上送）
② 服务端 SignalingCoordinator：L1/L2 授权校验 → 创建 sessionId → 向 B 下发
   PunchInvite{A 设备信息(含 staticPubKey), A 端点, N, relayAllowed}（第一段下发）
   B 离线/邀请不可达 → Error 4005 TARGET_OFFLINE，A 立即 failed 不等超时
③ B（被邀请方，哑节点亦可）收到邀请 → 即时 STUN/UDP Binding 得 B 端点 →
   PunchEndpoint{sessionId, B 端点}上报；不等待中转，立即开始向 A 端点连发 PTP THello1
   （打洞包=隧道首包，合一减少 RTT）
④ 服务端收到 B 端点 → 向 A 下发 PunchRequest Ack{B 设备信息(含 staticPubKey), B 端点,
   N, relayAllowed}（第二段）→ A 开始向 B 端点连发 THello1
⑤ 双向命中 → 完成 4.1 握手 → 隧道建立
⑥ 承载协商（NET-77，握手成功瞬间——caps 判定开火前已完成，两端同式 kcpEnabled=(myCaps&peerCaps&CAP_KCP)!=0 仅本地输入无第三态）：true → KcpTunnelTransport.Adopt(socket, pinnedEndpoint)（socket 所有权移交）→ FromEstablishedKeys 接 KCP 承载（M2-16 缝）；false → 现状裸 UdpPunchTransport 路径逐字节不动。承载与会话同生共死、中途不可切换（§4.5），断链重建时重新协商（§4.6）
超时 10s（可配）→ 失败 → 按该目标设备的设备级回退配置决定 0x74 中继（OQ-10）
```

### 5.2 TCP 打洞（端口预测，并发路数 N）

```
① A（访问方）从专用本地端口 L 发 TCP Binding 到 STUN:3478 → 得映射 (公网IP:portTcp)
   （此 TCP 连接用完即关；本地端口 L 由应用持有，记录复用）
   → PunchRequest 上送 requesterEndpoints.tcp（OQ-18 第一段）
② PunchInvite（发往 B）携带：发起方公网 IP、portTcp、并发路数 N、sessionId；
   B 收到后同样从专用本地端口发 TCP Binding 探测 → 0x76 PunchEndpoint 上报 →
   服务端经 PunchRequest Ack 把 B 端点转交 A（两段式互换完成，同 §5.1②~④）
   N 取**发起方（访问方）客户端配置**（FR-C-808），经 PunchInvite 统一下发，双方该次打洞
   必须执行同一 N——对称性硬约束 N_A=N_B：A 的目标偏移须命中 B 的第 (N−1) 条连接产生的
   端口分配，反之亦然；双方 N 不一致则预测基准错位、必然 miss
③ 双方各自执行（对称，缺一不可——TCP simultaneous open，见实现备注）：
   a. 在本地端口 L 上 listen（SO_REUSEADDR）
   b. 并发发起 N 条 connect（**波次补射**，2026-10-24：打洞窗内每 800ms 重建一波，
      每波全新 socket=全新 SYN 预算），目标统一为 对端 (公网IP : portTcp + (N−1))；
      本地端口取 N 个不同端口：每波首条在 L 槽空闲时沿用 L，其余由系统分配
      N=1→+0（直连 STUN 端口）；N=2→+1；N=3（默认）→+2；N=4→+3；N=5→+4（上限）
④ 任一 connect 成功 或 listen 收到入连接 → 立即在该连接上执行 PTP 握手（4.1）
   首个完成握手的连接胜出，关闭其余连接
⑤ 齐射同步（0x77 PunchFire，2026-10-24）：③b 的 connect 首波不即发——
   A 以 0x70 Ack 到达为锚、B 以同刻下发的 0x77 为锚，各倒数同一 Δ=400ms 到点齐射，
   SYN 在空中交叉；规避「B 建池即打、早于 A 映射建立打空门」（RST 即死+Windows SYN
   重传预算仅 ~2 次）竞态。0x77 丢失/旧服务端 → B 等待器超时（600ms）兜底立即开火，
   残余时差由波次补射覆盖
⑥ 超时 10s 失败 → 同 5.1 ④
```

实现备注：

- **双方必须同时发包（TCP simultaneous open）**：对端 NAT 只有在自己发出出站连接后才存在"可被命中的外部端口映射"，单侧 connect 的 SYN 会被对端 NAT 丢弃/拒连；双方各自 listen + 并发 connect，两条 SYN 在两台 NAT 间交叉后按 TCP 同时打开语义完成握手。齐射时刻以**同锚点倒计时**对齐（⑤：B=收到 0x77、A=收到 0x70 Ack——两消息由服务端同刻背靠背下发，开火时刻差≈两条控制连接的投递时差；2026-10-24 前旧口径「B 收到 PunchInvite 即打、小时差靠 SYN 重传覆盖」已废止——两段式信令引入的秒级时差超出 Windows SYN 重传预算（默认仅 ~2 次，~2-3s 即放弃），公网实测必现「B 早打 A 空门→RST 互杀」，用户手工同时开火可成而程序不成的实证即此）；
- **波次补射（③b，2026-10-24）**：一次性齐射改为窗口内每 800ms 重建一波——死波（被 RST 拒/超 SYN 预算）由下一波以全新 socket 接替，任意一波落在「对端瞄准点槽位存活（SYN_SENT 重传窗）」时段即成交；本端 NAT 落点区间随波次上移，但双方瞄准点取自 STUN 观察基准、不随波次变化，由对方首波槽位承载（一方齐射命中对方活槽即单向成交，两侧对称互补）。每波 L 槽规则：在飞的 L 槽 connect 未结束才由本波首条重新 bind L；
- **本地端口分配（实现约束）**：第 1 条 connect 沿用 STUN 探测端口 L（`SO_REUSEADDR`，Windows `SocketOptionName.ReuseAddress`；Linux 需 `SO_REUSEADDR + SO_REUSEPORT`），保持与 STUN 探测的 NAT 端口分配序列衔接；其余 N−1 条**必须使用不同本地端口**——同源端口连向同一目标端口构成重复四元组，OS 自第 2 条起拒绝建立。N 条连接整体恰好消耗本端 NAT 在 STUN 探测之后的 N 个顺序端口分配；
- N 条并发连接目标端口统一为 `portTcp+(N−1)`（PRD OQ-1 决议原文）；实现层将偏移量抽取为 `int[] Offsets` 常量（当前为单元素 `[N−1]`），保留扩展多偏移的能力而不改变协议；
- **承载分帧（M2-16 随编码定案）**：直连 TCP 打洞胜出连接的 PTP 会话承载与 §6.2 中继 TCP 承载复用同一定界——`[u16 帧长（小端）][PTP 帧]`；帧上限 = 16B 帧头 + 16KiB DATA 载荷上限（§4.3）+ 16B AEAD tag = **16416B**：发送侧越界拒绝（协议异常），接收侧前缀越界/中途截断视为流错位按承载关闭处理（同 UDP 承载关闭契约）；
- A-5 验收将实测 N=1~5 命中率差异，数据进基准报告（09 §4）。
- 直连优先（NET-76，v1.63）：N 条预测 connect 之外并行对「对端映射端点偏移 0 ∪ 对端候选」各起拒连重试探测（预测 connect 必须先发，§5.4）。

### 5.3 NAT 保活

- 直连 UDP 路径：PTP KEEPALIVE 20s；
- STUN 映射不作长持（打洞期内瞬时使用）；
- 中继路径：同样 KEEPALIVE 维持 relay 会话（05 §6）。

### 5.4 直连优先与候选地址交换（NET-76，v1.63 2026-10-21）

> 用户需求：打洞时先判断两机可否 IP 直连（①同局域网互通 ②一方有公网 IP 对方可直达）。现状盲区：信令只互换 STUN 公网映射端点——同局域网时对端内网 IP 不可知（发夹 NAT 通常还不通）；TCP N 条预测 connect 统一瞄「对端映射端口+(N−1)」（§5.2③b），对端有公网 IP（映射口=真实监听口）时瞄 +(N−1) 必偏。**决策（用户批复）：并行竞赛**——不新增常驻监听，复用打洞会话本身的随机监听口（TCP 端口 L / UDP 打洞 socket），候选=本机网卡 IPv4 × 该监听口；直连可达时即刻胜出，均不可达时行为与现状一致、零额外时延（加密握手的对端公钥本就须经信令交换，直连探测无需额外信任引导）。

- **候选构造**：`PunchOptions.BindAddress` 非空 → `[BindAddress]`（NatSimulator 回环别名拓扑可测）；否则复用 `P2P.Nic.SubnetSurvey` 地址快照，滤 `100.64.0.0/10` 虚拟网段、去重、上限 8 个；枚举异常降级空集（退化为纯映射路径）。
- **候选交换**（复用两段式，§2.4 四行字段；服务端纯存转零解析）：A 的候选随 0x70 上送 → PunchInvite.localCandidates 透传给 B；B 的候选随 0x76 上送 → 0x70 Ack.peerLocalCandidates 透传给 A。字段全部可空——旧端（133102 等未升级）不携带/不解析，任一侧缺候选即退化为纯映射路径，混布不打断（§7 演进规则，同 punchConcurrency 先例）。
- **UDP（§5.1 增量）**：握手包向「映射端点 ∪ 对端候选」全扇出（并行竞赛）；首个到达包把回程**钉定**到其源端点（pin-on-receive）——此后只发该端点，对端经内网收到 THello1 后 THello2 也从内网回，不绕映射端点发夹；结果端点（0x72 上报/日志）取钉定后的实际可达对端。
- **TCP（§5.2 增量）**：directTargets=「对端映射端点原样（偏移 0）∪ 对端候选」（去重、剔除与预测目标相同者——N=1 时偏移 0 与预测同点即免）；**对端候选 null/空（旧端未携带/枚举降级）→ 直连探测整体跳过、退化为纯映射路径**（混布口径的执行点——无条件瞄偏移 0 会击穿 NatSimulator 探测映射可入的必败场景前提[TD-21]，亦与「行为与无候选时一致」约束对齐）。每目标独立 `DirectProbeAsync`：connect 成功入池即握手；**仅 SocketException 拒连（RST）时以 250ms 步进重试至打洞窗收尾**（覆盖对端监听口晚就绪竞态），DROP 型静默丢弃由 OS 级 SYN 重传覆盖；计数 DirectRefused 与预测 connect 失败（FailedConnects）分账。onConnection 扇出移入 AddConnection 统一触发——accept 侧连入也即时发 THello1（对端公网/同网段可达时连入即握手，不依赖周期补发窗）。
- **顺序约束**：N 条预测 connect **必须先发**、直连探测后发——直连探测若先发会吞掉本端 NAT 顺序分配端口、污染 +(N−1) 预测基准（与 §5.1 打洞调度串行化同理）；测试缝 `ClientRuntimeOptions.LocalIpEnumeratorOverride` 供 NatSimulator 场景显式启停候选（回环别名 fabric 全互通，默认须关保必败场景前提）。
- 测试口径（09）：SignalingTests 候选透传/旧端 null 2 例；TcpPunchFleet 直连命中/拒连重试/DirectRefused 分账/accept 扇出；Puncher 恒等映射 N=3（旧实现必 miss 红绿证据）+映射平移候选唯一活路；PunchTests UDP 双假映射样候选+pin 回程；集成 S54 同网段（对照组候选关→failed）。

## 6. RLP · 中继协议

### 6.1 会话建立

```
① 打洞失败且该目标设备的设备级回退配置开启（OQ-10）→ 访问方发 RelayAllocate{sessionId}（0x74）
② 服务端中继分配 relaySessionId，向双方下发 RelayGrant{udpEndpoint, tcpEndpoint, relaySessionId}
③ 双方各自向 relay 发 RELAY_JOIN：
   UDP: 单发 [u8 0x01][u64 relaySessionId][u32 nonce] 直到收到 [0x02] 确认（学习双方地址）
   TCP: 建立长连接，首帧同上（分帧 u16len）
④ 加入完成后，双方到 relay 的每个包：
   [u64 relaySessionId][PTP 密文帧（原样）]
   relay 校验 relaySessionId 存在 → 剥离外层 8B → 转发给会话另一端最后已知地址，并以其源地址更新该端地址
```

### 6.2 约束

- relay **只解析外层 8B 会话头**，帧内全部为密文（TD-11，SEC-11 中继不可解密）；
- TCP 承载（**JOIN 默认优先**，M2-38；UDP 为 7020 被封场景兜底，FR-S-704 承载可异构不变）：双方与 relay 建 TCP，PTP 帧以 u16 长度前缀承载，UDP_DGRAM 语义不变。优先级反转动机（公网实测 M2-38）：UDP 承载无重传——并发大流量丢 DATA 帧（对端字节流缺段、应用收不满 Content-Length 卡死）/WINDOW 信用回报（发送侧信用耗尽永久挂起）/OPEN 控制帧（连接即断）；单流轻载不易察觉，多 channel 并发 burst 放大；
- relay 会话空闲 90s 回收；限速（FR-S-703）= 每会话/全局令牌桶，超限丢弃并计数；
- 回切直连（OQ-7）：中继态每 60s 由访问方发起 `PunchRetry`（0x73）；直连握手成功后按 NET-75 排水切换：旧中继路径在途帧处理完毕（2s 接收窗口）后关闭；重打失败而设备对活中继会话仍在 → 复用既有中继承载不重新 0x74 分配（M2-37：周期性整体替换会杀死跨周期传输中连接——复用决定先于分配作出，发起侧不分配则被动侧不重建，05 §4 服务连续性）。
- 非目标（NET-77 范围界定，M6）：中继 UDP（7010）承载可靠化属二期——中继默认 TCP 承载（上行），UDP 承载仅兜底；KCP 可靠层本期只覆盖 UDP 直连承载（11 号 §1.3，二期复用 KcpTunnelTransport）。

实现注记（M2-07 落地）：

- **地址学习仅经 RELAY_JOIN 认领**（§6.1④ 的"源地址更新"收窄为认领时刷新）：数据包源地址不匹配
  已认领两端即**丢弃**（保守不学习，防会话劫持）；地址变更（NAT 重绑定）由客户端重新 JOIN 覆盖，
  逾期场景由空闲回收 + 重新 allocate 兜底。
- **0x74 错误路径**：relay_enabled=0 → `5002 RELAY_DISABLED`；打洞会话台账缺失或申请方非发起方 →
  `1001 session_unknown`（台账 = 会话结束后服务端保留 120s 的 sessionId→设备对）；对端离线 → `4005`。
- **端点派生**：RelayGrant 端点 host 优先取 `public_addr` 通告地址（03 §2.8，非空时——NAT 云部署
  必配，M2-36；空 = 各客户端控制连接的服务端本地侧地址，经哪个接口到达回哪个地址）；
  转发承载对端 TCP 优先、次选已学 UDP 地址，对端未 JOIN 期间无缓冲丢弃。
- **TCP 端语义**：首帧 JOIN 10s 超时；数据帧会话头与认领连接不符即断连（AI-19）；任端 TCP 断连
  = KEEPALIVE 停止 → 会话即时回收并关闭对端连接。

## 7. 版本与兼容策略

| 项 | 策略 |
|---|---|
| 协议版本 | `protocolVersion` 单调递增；不兼容变更递增主版本，服务端保留**相邻旧版本**兼容窗口 |
| 冻结字段 | `Hello.protocolVersion`、`UpdateInfoRequest`（升级引导链路永不变更，TD：4.3/2.4） |
| 消息演进 | 仅允许"新增 msgType / 新增可选字段（尾部新增、旧端忽略——MessagePack 尾部容忍；v1.67 勘误：原注「map 兼容」措辞不准，实现为整型 Key 数组格式）"，禁止删改既有字段语义 |
| 拒绝策略 | 版本不兼容 → `VERSION_NOT_SUPPORTED` + 仍可应答 UpdateInfo，随后断开 |
| 行为类变更 | 安全策略类**行为**硬切（如 M5 登录族拒收明文，OQ-21①）不属格式破坏、**不递增 protocolVersion**，须 02 载荷行+07 双册记录口径；「相邻旧版本兼容窗口」仅适用于版本递增后的旧协议**格式**兼容，不得用作弱算法/明文回退通路（07 §15.3 演进纪律） |
