# 02 · 通信协议设计

> 所属文档集：[README](README.md)　编码：MessagePack（TD-05）；多字节整数小端；所有协议版本号 `v1`。

## 1. 协议总览

| 协议 | 承载 | 用途 | 对应 PRD |
|---|---|---|---|
| PCP（P2P Control Protocol） | TCP 7000 长连接 | 注册、鉴权、心跳、设备/分组数据、打洞信令、配置同步 | FR-S-1xx~8xx |
| STUN-R（RFC 5389 子集） | UDP/TCP 3478 | 公网端点探测（带设备认证扩展属性） | FR-S-601/602/603 |
| PTP（P2P Tunnel Protocol） | UDP/TCP（打洞成功路径） | 端到端加密、channel 复用、保活、密钥轮换 | SEC-11~14、NET-7x |
| RLP（Relay Protocol） | UDP/TCP 7010+ | 中继会话接入与密文转发 | FR-S-701~704 |

## 2. PCP · 控制协议

### 2.1 分帧

```
+----------------+----------------------+
| u16 bodyLen    | MessagePack(body)    |
+----------------+----------------------+
bodyLen ≤ 64 KiB；单连接串行处理；TCP NoDelay 开启。
列表类大消息（如 0x40）**必须应用层分页**（OQ-16，见 0x40），禁止依赖超限帧或协议层续传。
```

### 2.2 消息公共头（每个 MessagePack body 首字段）

```
record MsgHeader(
    u32 seq,            // 连接内单调递增
    u64 timestampMs,    // 校准后时钟 ±120s 窗口外被拒（防重放，SEC-22；时钟对齐见 2.3）
    u8  msgType,
    ...payload)
```

每条消息尾部附 `hmac: bytes[32] = HMAC-SHA256(connMacKey, header||payload)`；`connMacKey` 由握手派生（见 2.3）。**未注册设备的首个 `Register` 消息例外**：无连接密钥，不携带 hmac，靠注册开关/限速防滥用（07 §5）。

### 2.3 连接握手（时序）

```
C → S: Hello { protocolVersion, deviceId?, nonceC }               // 不校验 ts（尚无共享时间基准）
S → C: HelloAck { serverVersion, protocolVersion, nonceS, status, serverTs }
       status = OK | NEED_REGISTER | VERSION_NOT_SUPPORTED(→ 触发升级引导 FR-C-904)
C:    时间对齐（OQ-12）：RTT = t(收到HelloAck) − t(发出Hello)；
       offset = serverTs + RTT/2 − t(收到HelloAck)   // 传输耗时按 RTT 半程补偿
       此后全部消息 timestampMs 以 本地时间 + offset 生成（STUN DEVICE-AUTH 同用此 offset）
C → S: Proof { hmac = HMAC(deviceSecret, nonceC|nonceS) }        // 注册过的设备；ts 校验自此生效
S → C: ProofAck { ok }
       connMacKey = HKDF-SHA256(deviceSecret, nonceC|nonceS|"pcp-mac")
       ts 超窗 → Error 5005 TIME_SKEW{serverTs}，客户端重算 offset 后重试一次
```

- `Hello.protocolVersion` 字段位置与语义**永久冻结**（TD：升级引导依赖，PRD FR-S-804）；
- `VERSION_NOT_SUPPORTED` 时服务端仍接受 `UpdateInfoRequest`（见 2.4），随后由客户端主动断开；
- 时钟对齐持续维护：0x30 Ack 的 `serverTs` 周期性重算 offset（跟踪本机时钟漂移；异常跳变时重新握手对齐）。

| 0x74 | RelayAllocate / Grant | C↔S | {sessionId} → {relayEndpoint(udp/tcp), relaySessionId} |
| 0x75 | Invalidation | S→C | 授权/状态失效推送（PRD 05 §4 任意层失效的执行载体）：{ reason: logged_out\|user_disabled\|device_disabled\|remote_code_reset\|lan_segment_removed\|group_left\|group_dissolved, affectedMappingIds[], newCapability? }；收到后客户端将受影响映射置 invalid 并停止转发（FR-C-702、FR-S-903/204/105） |

| 0x7E | Error | S→C | {code, httpLikeMsg}（错误码表见 04 §5） |

### 2.5 哑节点约束的执行点（PRD 05 §3）

服务端 `ControlSession` 维护能力模式；**主动类**消息 `0x20/0x21/0x23/0x40/0x50~0x57/0x60/0x70`（用户与分组管理、列表查询、映射、打洞发起）在 passive 模式下直接回 `Error(FORBIDDEN_PASSIVE)` 并写审计日志（SEC-51）。**本机管理与被动同步类** `0x13/0x14/0x30/0x62/0x63/0x64` 正常受理（PRD 05 §3 矩阵）。

## 3. STUN-R · STUN 子集（RFC 5389）

### 3.1 范围

- 仅实现 **Binding Request/Success Response**；不做长期凭据/TURN 扩展；
- 报文头 20B：`type(2) msgLen(2) magicCookie(4)=0x2112A442 transactionId(12)`；
- 响应属性：`XOR-MAPPED-ADDRESS (0x0020)`；请求须携带自定义认证属性。

### 3.2 设备认证扩展属性（FR-S-603）

```
Attribute 0x8020 DEVICE-AUTH:
  deviceId(16B) + nonce(16B) + ts(8B) + HMAC-SHA256(deviceSecret, deviceId|nonce|ts|transactionId)(32B)
```

- 不通过则静默丢弃（UDP）/ 关闭连接（TCP），不回应；
- ts 窗口 ±120s（使用 §2.3 校准 offset），nonce 去重缓存 5 分钟（防重放）。

### 3.3 TCP Binding 的使用约定（TCP 打洞数据源）

客户端以**专用本地端口 L** 发起 TCP 到 STUN:3478，完成一次 Binding 事务后**立即关闭**；得到的映射即 `L→L'`。该本地端口 L 随后被用于 TCP 打洞的 listen+connect（见 §5.2）。

## 4. PTP · 隧道协议（端到端加密）

### 4.1 会话密钥握手（打洞成功后立即执行）

双方 static 密钥（P-256）公钥已经服务端 `PunchInvite` 交换（受服务端信任通道保护，SEC-13）。

```
A → B: THello1 { sessionId, ephA(P-256公钥), nonceA }
B → A: THello2 { ephB, nonceB, mac = HMAC(kBS_static共享, hash(THello1||THello2前文)) }
A → B: TConfirm { mac = HMAC(kAS_static共享, hash(全部前文)) }

k_static = ECDH(staticA, staticB)                       # 身份绑定（服务端分发的公钥）
k_sess   = HKDF-SHA256(ikm = ECDH(ephA,ephB) || k_static,
                       salt = sessionId|nonceA|nonceB,
                       info = "ptp-v1",
                       len  = 64)                        # 前32B=发送密钥A→B，后32B=B→A
```

- 双重 ECDH（ephemeral-ephemeral + static-static）：静态部分绑定设备身份防冒充，临时部分提供会话独立性；
- 静态-静态 ECDH 仅用于握手认证，不直接加密业务数据。

### 4.2 帧格式

```
+------+------+-----------+---------+--------+==================+
| ver  | type | channelId | counter | u16len |   AEAD 密文       |
| u8=1 | u8   | u32       | u64     |        |  (含16B GCM tag)  |
+------+------+-----------+---------+--------+==================+
AEAD = AES-256-GCM(key=会话方向密钥, nonce=counter 的12B小端, aad=帧头明文部分)
counter 每方向独立计数、严格递增；收到重复/回退计数即丢弃并告警（防重放，SEC-12）
```

| type | 名称 | 说明 |
|---|---|---|
| 0x01 | OPEN | 建 channel：{targetProto, targetAddr, targetPort}（访问方向对端申请打开目标连接） |
| 0x02 | OPEN_OK / OPEN_FAIL | 对端连接目标的结果；FAIL 携带原因码 |
| 0x03 | DATA | 流数据（TCP 映射） |
| 0x04 | CLOSE | 关闭 channel（正常/异常） |
| 0x05 | KEEPALIVE | 20s 周期（NET-72 ≤25s）；对端回 KEEPALIVE |
| 0x06 | PING / PONG | RTT 测量（本地 Web 诊断页用） |
| 0x07 | REKEY | 密钥轮换（见 4.4） |
| 0x08 | UDP_DGRAM | UDP 映射数据报帧 {channelId, payload}（M2，FR-C-303；目标地址已由 OPEN 固定，channel 生命周期见 05 §2.4/TD-15） |
| 0x09 | WINDOW | channel 流控信用（M2；M1 先用有界缓冲+背压，见 05 §2.3） |
| 0x0A | FRAG | DATA 分片标记位承载于 DATA 头（UDP 承载时帧总长 ≤1400，超出分片） |

### 4.3 复用与背压

- 一条隧道复用设备对之间**全部映射与全部应用连接**的 channel（channelId 由发起侧分配，32bit 随机起点避碰撞；生命周期规则见 §4.5）；
- TCP 直连承载时无 MTU 限制，DATA 上限 16 KiB；UDP 承载时帧 ≤1400B；
- 背压：M1 = 同步 splice + 每 channel 有界发送队列（满则暂停读取本地 socket，TCP 自然反压）；M2 = WINDOW 信用机制。
- 混淆扩展点（FR-C-503/SEC-15，P2 不实现）：帧格式外层预留传输包装层——`IObfuscationAdapter`（直通/混淆两种实现），首版直通透传；后续可插入 udp2raw 类伪装而不改动 PTP 帧格式与加密层。

### 4.4 密钥轮换（SEC-14）

- 会话密钥 TTL 默认 3600s（可配）或手动触发；
- 到期由会话发起方发 `REKEY { 新 eph 公钥, nonce }`，对端回 `REKEY_ACK`，按 4.1 相同方式派生新密钥；
- 切换遵循**先排水后切换**（NET-75）：新密钥生效后旧密钥保持接收窗口 2s 排空在途帧，然后销毁。

### 4.5 隧道生命周期与打洞次数（设备对粒度）

| 规则 | 说明 |
|---|---|
| 粒度 | 隧道是**设备对级**资源：A↔B 同一时刻至多一条活跃隧道；全部映射、每条映射的每个本地连接（channel）都复用它，**不按连接/映射分别打洞** |
| 建立 | 首个需要到达对端的映射 enable 且无可用隧道时，发起一次 PunchRequest → 打洞 → PTP 握手 |
| 复用 | 隧道存活期间，任何新映射启用、新应用连接接入，直接在既有隧道上 OPEN 新 channel（无信令、无打洞、无重新握手） |
| 承载绑定 | UDP 打洞成功 → UDP 承载；TCP 打洞成功 → TCP 承载；均失败 → 按访问方对**该目标设备的设备级回退配置**（D3 v0.4/OQ-10，客户端本地 peers.json）决定：开启 → 中继（同一 TunnelSession 的备用路径）；未开启 → 该设备对全部映射 failed。后续映射复用当前承载，不重复尝试其他方式（隧道重建时才重新竞争） |
| 重建 | keepalive 连续 3 次无响应 / 底层 socket 故障 → 隧道销毁（新 sessionId、计数器清零）→ 各引用映射状态机回 punching → 重新打洞 |
| 空闲回收 | 无活跃 channel 且无启用中映射 → 空闲 300s（可配）优雅关闭（先排水，NET-75）；下次需要时重新打洞 |
| 中继会话 | RelayAllocate 同样以设备对为粒度（回退与否由设备级配置门控，见上行）；中继态 60s 直连重试成功按"路径切换"处理，不新建隧道 |

设计动机：① 打洞成本高（信令往返 + 每次消耗双方 NAT 的 N 个顺序端口分配，频繁打洞会推远预测基准）；② 一条路径一份 20s 保活；③ 一套会话密钥，REKEY 简单；④ 多映射共享路径、按 channel 计量。

## 5. 打洞交互（D10 / OQ-1 决议的实现细节）

### 5.1 UDP 打洞

> 打洞调度（OQ-11）：客户端 PunchScheduler 全局**串行队列**（05 §3）——上一会话完成/超时后才执行下一个，避免多目标并发打洞交叉消耗本端 NAT 顺序端口分配、污染 +(N−1) 预测基准；服务端 SignalingCoordinator 同时保证**同一目标设备至多一个活跃打洞会话**（并发申请排队/合并，05 §5）。
> 端点互换（OQ-18，**两段式**）：STUN 映射仅打洞期内瞬时使用（§5.3 不长持），服务端无从预知双方端点，由本轮信令**现场收集互换**——发起方端点随 0x70 上送（第一段），被邀请方端点经 0x76 回传、由 0x70 Ack 送达发起方（第二段）。

```
① A（访问方）PunchScheduler 出队 → 即时向 STUN:3478/UDP 发 Binding → 得 A 端点
   → PunchRequest{..., requesterEndpoints}（第一段上送）
② 服务端 SignalingCoordinator：L1/L2 授权校验 → 创建 sessionId → 向 B 下发
   PunchInvite{A 设备信息(含 staticPubKey), A 端点, N, relayAllowed}（第一段下发）
   B 离线/邀请不可达 → Error 4005 TARGET_OFFLINE，A 立即 failed 不等超时
③ B（被邀请方，哑节点亦可）收到邀请 → 即时 STUN/UDP Binding 得 B 端点 →
   PunchEndpoint{sessionId, B 端点}上报；不等待中转，立即开始向 A 端点连发 PTP THello1
   （打洞包=隧道首包，合一减少 RTT）
④ 服务端收到 B 端点 → 向 A 下发 PunchRequest Ack{B 设备信息(含 staticPubKey), B 端点,
   N, relayAllowed}（第二段）→ A 开始向 B 端点连发 THello1
⑤ 双向命中 → 完成 4.1 握手 → 隧道建立
超时 10s（可配）→ 失败 → 按该目标设备的设备级回退配置决定 0x74 中继（OQ-10）
```

### 5.2 TCP 打洞（端口预测，并发路数 N）

```
① A（访问方）从专用本地端口 L 发 TCP Binding 到 STUN:3478 → 得映射 (公网IP:portTcp)
   （此 TCP 连接用完即关；本地端口 L 由应用持有，记录复用）
   → PunchRequest 上送 requesterEndpoints.tcp（OQ-18 第一段）
② PunchInvite（发往 B）携带：发起方公网 IP、portTcp、并发路数 N、sessionId；
   B 收到后同样从专用本地端口发 TCP Binding 探测 → 0x76 PunchEndpoint 上报 →
   服务端经 PunchRequest Ack 把 B 端点转交 A（两段式互换完成，同 §5.1②~④）
   N 取**发起方（访问方）客户端配置**（FR-C-808），经 PunchInvite 统一下发，双方该次打洞
   必须执行同一 N——对称性硬约束 N_A=N_B：A 的目标偏移须命中 B 的第 (N−1) 条连接产生的
   端口分配，反之亦然；双方 N 不一致则预测基准错位、必然 miss
③ 双方各自执行（对称，缺一不可——TCP simultaneous open，见实现备注）：
   a. 在本地端口 L 上 listen（SO_REUSEADDR）
   b. 并发发起 N 条 connect，目标统一为 对端 (公网IP : portTcp + (N−1))；
      本地端口取 N 个不同端口：第 1 条沿用 L，其余 N−1 条由系统分配
      N=1→+0（直连 STUN 端口）；N=2→+1；N=3（默认）→+2；N=4→+3；N=5→+4（上限）
④ 任一 connect 成功 或 listen 收到入连接 → 立即在该连接上执行 PTP 握手（4.1）
   首个完成握手的连接胜出，关闭其余 N−1 条
⑤ 超时 10s 失败 → 同 5.1 ④
```

实现备注：

- **双方必须同时发包（TCP simultaneous open）**：对端 NAT 只有在自己发出出站连接后才存在"可被命中的外部端口映射"，单侧 connect 的 SYN 会被对端 NAT 丢弃；双方各自 listen + 并发 connect，两条 SYN 在两台 NAT 间交叉后按 TCP 同时打开语义完成握手。发起时刻由服务端信令协调对齐（B=收到 PunchInvite、A=收到 PunchRequest Ack，OQ-18），小时差靠 SYN 重传覆盖；
- **本地端口分配（实现约束）**：第 1 条 connect 沿用 STUN 探测端口 L（`SO_REUSEADDR`，Windows `SocketOptionName.ReuseAddress`；Linux 需 `SO_REUSEADDR + SO_REUSEPORT`），保持与 STUN 探测的 NAT 端口分配序列衔接；其余 N−1 条**必须使用不同本地端口**——同源端口连向同一目标端口构成重复四元组，OS 自第 2 条起拒绝建立。N 条连接整体恰好消耗本端 NAT 在 STUN 探测之后的 N 个顺序端口分配；
- N 条并发连接目标端口统一为 `portTcp+(N−1)`（PRD OQ-1 决议原文）；实现层将偏移量抽取为 `int[] Offsets` 常量（当前为单元素 `[N−1]`），保留扩展多偏移的能力而不改变协议；
- A-5 验收将实测 N=1~5 命中率差异，数据进基准报告（09 §4）。

### 5.3 NAT 保活

- 直连 UDP 路径：PTP KEEPALIVE 20s；
- STUN 映射不作长持（打洞期内瞬时使用）；
- 中继路径：同样 KEEPALIVE 维持 relay 会话（05 §6）。

## 6. RLP · 中继协议

### 6.1 会话建立

```
① 打洞失败且该目标设备的设备级回退配置开启（OQ-10）→ 访问方发 RelayAllocate{sessionId}（0x74）
② 服务端中继分配 relaySessionId，向双方下发 RelayGrant{udpEndpoint, tcpEndpoint, relaySessionId}
③ 双方各自向 relay 发 RELAY_JOIN：
   UDP: 单发 [u8 0x01][u64 relaySessionId][u32 nonce] 直到收到 [0x02] 确认（学习双方地址）
   TCP: 建立长连接，首帧同上（分帧 u16len）
④ 加入完成后，双方到 relay 的每个包：
   [u64 relaySessionId][PTP 密文帧（原样）]
   relay 校验 relaySessionId 存在 → 剥离外层 8B → 转发给会话另一端最后已知地址，并以其源地址更新该端地址
```

### 6.2 约束

- relay **只解析外层 8B 会话头**，帧内全部为密文（TD-11，SEC-11 中继不可解密）；
- TCP 承载（UDP 被封场景，FR-S-704）：双方与 relay 建 TCP，PTP 帧以 u16 长度前缀承载，UDP_DGRAM 语义不变；
- relay 会话空闲 90s 回收；限速（FR-S-703）= 每会话/全局令牌桶，超限丢弃并计数；
- 回切直连（OQ-7）：中继态每 60s 由访问方发起 `PunchRetry`（0x73）；直连握手成功后按 NET-75 排水切换：旧中继路径在途帧处理完毕（2s 接收窗口）后关闭。

## 7. 版本与兼容策略

| 项 | 策略 |
|---|---|
| 协议版本 | `protocolVersion` 单调递增；不兼容变更递增主版本，服务端保留**相邻旧版本**兼容窗口 |
| 冻结字段 | `Hello.protocolVersion`、`UpdateInfoRequest`（升级引导链路永不变更，TD：4.3/2.4） |
| 消息演进 | 仅允许"新增 msgType / 新增可选字段（MessagePack map 兼容）"，禁止删改既有字段语义 |
| 拒绝策略 | 版本不兼容 → `VERSION_NOT_SUPPORTED` + 仍可应答 UpdateInfo，随后断开 |
