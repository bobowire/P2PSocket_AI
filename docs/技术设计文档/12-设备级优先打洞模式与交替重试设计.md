## 0. 摘要与决策记录

**一句话**：打洞协议不再由"首条触发映射的 proto"决定，上收为目标设备级本地配置 **punchMode**（`tcp`/`kcp`，默认 `tcp`，peers.json 本地真相；kcp=UDP 打洞路径+KCP 承载优先，见 §2.1 口径分层）——首次打洞按优先模式执行；打洞失败回退中继后由周期循环自动重试直连，重试协议**以优先模式为起点 TCP/KCP 交替**；Failed 态（未回退中继的失败映射）纳入同一循环自动重试；打洞成功/失败日志与设备页"隧道类型"列全链路标注协议。

**决策点**（明细见 §2，均经用户确认 2026-11-19）：

| # | 决策点 | 结论 | 章节 |
|---|---|---|---|
| ① | 协议决策权归属 | **设备级完全接管**——打洞协议一律按设备页 punchMode 走（值域 `tcp`/`kcp`，默认 tcp，见 §2.1 口径分层）；映射表单 proto 字段保留存档，但打洞不再读它 | §2.1 |
| ② | 交替序列起点 | **以优先模式为起点**——优先=tcp 时重试序列 tcp→kcp→tcp…；优先=kcp 时 kcp→tcp→kcp…（对称规则） | §2.2 |
| ③ | Failed 态自动重试 | **纳入 60s 周期循环**——与中继回切共用一个循环；仅重排打洞（Failed 态且有监听的映射），无监听失败仍归既有监听重试集（M2-24） | §2.3 |
| ④ | 打洞日志带协议（补充需求） | PunchOutcome 加 `Proto` 尾字段，A/B 两侧结果日志统一标注 `proto=tcp/udp` | §6 |
| ⑤ | 设备页隧道类型列（补充需求） | TunnelSession 四态判别 Bearer（relay/kcp/raw-udp/tcp），设备发现页新增"隧道类型"列 | §7 |

**边界总述**：本设计为**纯客户端功能**——控制协议 0x70~0x78 零语义变更（0x70 的 proto 字段随实际执行路径自动正确，服务端缺省容忍逻辑不变）、服务端零改动、punch_stats 统计自动正确（proto 取自 0x70 台账）。B 侧被邀请方协议由 0x71 的 `PeerEndpoints.Tcp` 槽位决定（`Puncher.RespondAsync` 既有判别），A 侧换协议打洞 B 侧自动跟随，无需任何改动。

**PRD 回流**（2026-11-19，v0.17）：NET-78（06 §7 能力级约束）、FR-C-405（04 §4.4 打洞执行）、FR-C-803 扩展（04 §4.8 设备发现——优先打洞模式开关+隧道类型列）、M7 里程碑行（09 §1，出口=本设计 §10 测试口径）；任务清单 M7 随实施编制。

## 1. 背景与现状缺陷

### 1.1 现状链（既有定案，引用不改写）

- **proto 决策链**：映射创建表单选 tcp/udp（06 映射页）→ `MappingConfig.Proto` → 映射启用/手动重试/断链重入时 `PunchScheduler.Enqueue(peer, mapping, proto)`（02 §4.5："隧道为设备对级资源，首条触发映射的 proto 决定打洞方式，缺省 udp"）→ `Puncher.InitiateAsync` 按 proto 分派 TCP/UDP 两条路径。同一设备对的多条映射可各自声明不同 proto，实际生效的是"首条触发"的那条——用户视角协议不可预期、不可调。
- **中继回切重试**：`ClientRuntime.RelayRetryLoopAsync`（PRD 06 §6，60s 周期、无次数上限、仅发起方 IsInitiator 触发）对 ViaRelay 会话重新入队打洞，proto 取该设备对 relay 态映射的 Proto（兜底 udp）——重试协议恒定，若该协议恰为本网络不可打洞形态将永远在同一形态上循环失败：典型如对称 NAT 下 UDP 互发的端点本身即过期地址（出站目标一换 NAT 即分配新端口）必败，而 TCP 打洞的 +0..+(N-1) 扇形端口预测恰为对称 NAT 顺序分配特性设计、反而有机会——两形态互补却被恒定协议锁死。
- **Failed 态无自动重试**：打洞失败且未回退中继（设备级 relayFallback=false 或回退失败）→ 映射停 Failed。仅三个再触发点：手动 `/api/mappings/retry`、控制通道重连沿补试一轮（缺陷批次 2 修 C）、隧道断链事件。7×24 无人值守场景下"一次失败=永久失败"。
- **日志无协议**：打洞结果四型日志（PunchScheduler.LoopAsync——"打洞成功/打洞失败/中继承载建立/中继承载复用"）均不含本次打洞使用的协议；TCP 路径有 `[punch-tcp]` 计划线/收尾线（P4 诊断缝），但结果线（运维最常看的）无从分辨 tcp/udp，交替重试落地后更无法核对序列是否符合预期。
- **隧道类型不可见（设备维度）**：诊断页隧道表"承载"列（06 Settings 页）仅三分：`中继 / 直连·KCP / 直连`——"直连"未区分 TCP/UDP；设备发现页（用户最常驻留的页面）完全没有隧道形态呈现，用户无从知晓某设备当前是直连（何种协议）还是中继。

### 1.2 目标

1. 设备页可按目标设备配置打洞优先承载（TCP/KCP 切换，默认 TCP），对后续所有打洞会话即时生效（发送时点取现值，同 KcpBearer kill-switch 口径）；
2. 中继回退后每 60s 自动重试直连，重试承载以优先模式为起点 TCP/KCP 交替——单一形态不可达的网络环境下另一形态仍有周期性机会；
3. Failed 态映射同样每 60s 自动重试（交替协议），无人值守自愈；
4. 打洞成功/失败日志标注协议；设备发现页新增"隧道类型"列（tcp / kcp / 裸 udp / 中继 四态）。

### 1.3 非目标

- 不改控制协议任何消息（0x70 proto 字段语义原样，只是取值来源变了）；
- 不改服务端（SignalingCoordinator/信令/统计零改动）；
- 不从映射表单移除"协议"字段（保留存档；其打洞决策语义由 02 §4.5 注记声明让渡，见 §12）；
- 无监听失败（listen_failed 等 Listener==null 形态）不纳入周期重试——归既有监听重试集（M2-24），避免周期性"先拆后建"全量重启用与重试集双重驱动叠加；
- 交替计数为内存态，不做持久化（进程重启=重试序列重新自优先模式开始，语义自洽，见 §4.4）；
- 不做并发双协议同时打洞（PunchScheduler 串行语义 OQ-11 不动——交替是"跨会话"的，不是"会话内"的）。

## 2. 决策记录

### 2.1 ① 协议决策权：设备级完全接管（2026-11-19 用户批复；v0.2 修正口径）

| 决策 | 内容 |
|---|---|
| 结论 | 打洞协议决策点从"入队携带映射 proto"上收为"出队执行时按目标设备 punchMode 解析"。`PunchScheduler.Enqueue` 的 proto 参数仅在 planner 未装配（测试/旧形态）时生效 |
| 备选否决 | **"仅显式设置后覆盖"**（未设置=跟随映射 proto）：需引入"未设置"第三态，UI 默认显示 tcp 与实际行为"跟随映射"语义割裂，用户无法从界面预判行为；**"映射 proto 优先、punchMode 兜底"**：与用户"先使用优先选择的协议打洞"的诉求直接相悖 |
| 行为变更声明 | **存量部署影响**：punchMode 默认 tcp ⇒ 升级后所有设备对首次打洞协议统一为 tcp（现状=各自映射的 proto）。此为用户明示接受的目标行为（"默认 tcp"），发布说明中注明 |
| 映射 proto 字段 | 保留于 MappingConfig/表单/0x60 同步协议不动（wire 兼容），仅打洞决策不再消费；后续若产品化可另行清理（非本期） |

**口径分层（v0.2 用户修正定案）**：用户视角的切换选项是 **TCP 与 KCP**——kcp 不是新的打洞传输，即 M6 的 UDP 打洞路径（`InitiateUdpAsync`）+ 承载协商 KCP 优先（两端 caps 判定通过走 KCP；任一端 kill-switch 关闭/旧端混布降级裸 UDP——M6-04 既有决议不变，kcp 模式不强制也不禁止降级）。两层口径与映射关系：

| 层 | 值域 | 说明 |
|---|---|---|
| 配置/展示层（punchMode、peers.json、设备页开关） | `tcp` / `kcp` | 用户视角：TCP 直连打洞 vs KCP（UDP 打洞+KCP 承载） |
| 执行/统计层（Puncher 分派、0x70 proto、punch_stats、PunchOutcome.Proto、结果日志） | `tcp` / `udp` | wire 与统计口径**零变更**——punch_stats 既有数据只含 tcp/udp，不引入新值污染对账 |
| 映射（PunchModePlanner 出队时单向完成） | `kcp → udp`、`tcp → tcp` | 双射；日志/统计/协议按执行层口径落 |

执行层不引入 `"kcp"` 值的理由：0x70 的 proto 会被服务端原样存入打洞台账并落 punch_stats（SignalingCoordinator 缺省容忍仅对空值），新增 `"kcp"` 值将使 proto 列出现第三值，破坏既有 tcp/udp 二值口径的统计与对账。

### 2.2 ② 交替序列：以优先模式为起点（2026-11-19 用户批复）

- 优先=tcp：首次 **tcp**；重试序列 **tcp → kcp → tcp → kcp …**（执行层 tcp → udp → tcp …）
- 优先=kcp：首次 **kcp**；重试序列 **kcp → tcp → kcp → tcp …**（执行层 udp → tcp → udp …）

实现为计数取模：第 n 次重试（n 从 0 起）`n % 2 == 0 ? punchMode : 另一模式`（tcp/kcp 互补），返回前经 §2.1 映射转为执行口径。"手动重试/映射启用/断链重连"等新触发视为**新序列开始**（重置计数，用优先模式），仅周期循环触发的重试消耗交替序列（触发点分类见 §5.4）。

### 2.3 ③ Failed 态纳入周期重试（2026-11-19 用户批复，非保守项）

- 与中继回切**共用同一个 60s 循环**（`RelayRetryLoopAsync` 更名 `PunchRetryLoopAsync`，间隔常量与测试缝 `RelayRetryIntervalOverride` 名不动）：每 tick 先处理 ViaRelay 会话回切（现状逻辑），再遍历 Failed 态映射补一轮打洞重试。
- Failed 重试**仅重排打洞**（`MappingEngine.RetryPunchAsync`：Failed 态且有监听 → 置 Punching + EnqueueRetry），不做"先拆后建"全量重启用——无监听失败归 M2-24 监听重试集，防止双驱动叠加拆建抖动。
- 幂等安全：非 Failed 态 no-op；周期调用与手动重试/重连沿补试并发时由 PunchScheduler 同对合并（OQ-11）兜底去重。

### 2.4 ④⑤ 补充需求（2026-11-19 用户追加，随本期一并落地）

- **④ 打洞日志协议化**：结果可观测是交替重试的验收前提（无法从日志核对交替序列=功能不可验收）。PunchOutcome 加 `Proto` 尾字段，见 §6。
- **⑤ 隧道类型列**：设备发现页新增列显示当前设备对隧道形态（tcp / kcp / 裸 udp / 中继 / 无），数据复用既有 `GET /api/diagnostics/tunnels`（04 §2.6，passive 亦可达），见 §7。

## 3. 存储设计：peers.json 双字段（03 §5 扩展）

### 3.1 条目形态

```json
{
  "3f2b8a52-...（目标设备Id）": { "relayFallback": true, "punchMode": "kcp" }
}
```

- `PeerConfigDto` 增加 `public string? PunchMode { get; set; }`；内存快照 `IReadOnlyDictionary<Guid, bool>` → `IReadOnlyDictionary<Guid, PeerConfig>`，新增不可变记录：

```csharp
public sealed record PeerConfig(bool RelayFallback, string PunchMode); // PunchMode 规范化存 "tcp"/"kcp"（配置层口径，§2.1）
```

### 3.2 读取

- `GetPunchMode(Guid targetDeviceId) → string`：无条目/无文件 = `"tcp"`（决策①默认）；与 `GetRelayFallback` 同款快照无锁读。

现状 `SetRelayFallbackAsync` 整条目覆写——双字段后单字段写会丢另一字段。统一为**唯一写入口**：

```csharp
/// null = 保持现值（部分更新语义，同 SettingsApi PUT 口径）；punchMode 非 tcp/kcp 抛校验异常由 API 层转 Api.Fail。
```

- `SetRelayFallbackAsync` 改为 `SetAsync(deviceId, relayFallback: v)` 薄包装保留（PeersApi 之外无调用方，也可直接收敛到 SetAsync——实施时二选一，倾向后者减面）。

## 4. 协议规划器：PunchModePlanner（新组件）

### 4.1 形态

`src/P2P.Client/Punch/PunchModePlanner.cs`，纯内存小类，构造注入 `Func<Guid, string> punchModeLookup`（指向 `PeersStore.GetPunchMode`——**发送时点取现值**，设备页修改对后续打洞会话即时生效，与 KcpBearer kill-switch / punchConcurrency 同口径）：

```csharp
/// 设备级打洞协议规划器（设计 12 §4）：首次/新触发=优先模式并重置序列；周期重试=以优先模式为起点的交替。
/// 返回值为执行层口径（tcp/udp，§2.1 口径分层——punchMode="kcp" 出队映射为 "udp"）。
public sealed class PunchModePlanner
{
    private readonly Func<Guid, string> _punchModeLookup;
    private readonly Dictionary<Guid, int> _retryCount = []; // 设备对 → 已消耗的重试序号
    private readonly object _gate = new();                   // 调度循环与重试循环可能并发访问

    /// 新序列开始（映射启用/手动重试/断链/重连沿）：返回优先模式（执行口径），重置该设备对交替计数。
    public string Begin(Guid peerDeviceId);

    /// 周期重试取下一个协议（执行口径）：n=计数++，n%2==0 → 优先模式，否则另一模式；kcp/udp 映射在此完成。
    public string NextRetry(Guid peerDeviceId);
}
```

### 4.2 出队时点决策（关键口径）

交替计数**在 PunchScheduler 出队执行时消耗，不在入队时**：入队会因同对合并被静默丢弃（OQ-11：`Enqueue` 对已在队列/正在打的设备对 return false）——若入队时递增计数，被合并丢弃的入队会使序列跳号（如 tcp→tcp→udp 错序）。出队时点调用保证**每次真实执行的打洞会话才消耗一个序列号**。

### 4.3 planner 装配缝（测试兼容）

`PunchScheduler` 构造函数追加可选参 `PunchModePlanner? planner = null`：

- `null`（缺省）→ 维持旧行为（proto 用入队值）——**既有全部测试零改动**；
- 非 null → 出队时 proto 按下表解析：

| 入队形态 | 出队 proto |
|---|---|
| `Enqueue(...)`（普通，现状签名不动） | `planner.Begin(target)` —— **覆盖入队 proto**（决策①设备级接管） |
| `EnqueueRetry(target, trigger)`（新增） | `planner.NextRetry(target)` |

生产装配（ClientRuntime）：`new PunchScheduler(_puncher, new PunchModePlanner(_peers.GetPunchMode))`。

### 4.4 内存态语义

- 进程重启 → 计数归零 → 重试序列重新自优先模式开始。语义自洽：重启后首打本就是新序列（Begin），与"交替以优先模式为起点"一致；不做持久化（交替相位无运维价值，落盘反而引入状态一致性负担）。
- `EnqueueRetry` 在 planner==null 时的防御行为：使用入队占位 proto（默认 "udp"，即旧缺省口径）——生产不会发生（装配即成对），仅防御性兜底。

## 5. 调度与触发链改造

### 5.1 PunchScheduler（05 §3.1）

- Channel 元素 `(Guid Target, Guid? Trigger, string Proto)` → 追加 `bool Retry`；新增方法：

```csharp
/// 周期重试入队（设计 12 §5：中继回切/Failed 重试——出队时按 planner 交替序列解析协议）。
public bool EnqueueRetry(Guid targetDeviceId, Guid? triggerMappingId = null)
```

- 同对合并去重对 Retry/普通一视同仁（防周期重试与手动触发双打）。

### 5.2 MappingEngine：新增周期重试入口

```csharp
/// 周期失败重试（设计 12 §2.3）：仅 Failed 态且有监听的映射——置 Punching 并按交替协议重排打洞；
/// 无监听失败归监听重试集（M2-24）、非 Failed 态 no-op（幂等，供 60s 周期循环安全调用）。
/// 纯同步入队无异步面，返回 Task 与手动 RetryAsync 签名风格对称（CompletedTask）。
public Task RetryPunchAsync(Guid mappingId)
```

- 与手动 `RetryAsync` 的分工：`RetryAsync`（04 §2.5 /retry）语义不变——有监听 Failed 走 `Enqueue`（新序列 Begin），无监听走先拆后建全量重启用；`RetryPunchAsync` 只做前者且走 `EnqueueRetry`（交替），**绝不触发拆建**。

### 5.3 ClientRuntime：合并周期循环

`RelayRetryLoopAsync` 更名 **`PunchRetryLoopAsync`**（注释同步：中继回切 + Failed 重试统一周期循环；PRD 06 §6 的 60s 定值与测试缝 `RelayRetryIntervalOverride` 名不变）：

```csharp
while (await timer.WaitForNextTickAsync(ct))
{
    // ① 中继回切（现状逻辑不变，proto 计算三行删除——协议交由 planner 交替）
    foreach (var session in _host.Sessions.Where(s => s.ViaRelay && !s.IsClosed && s.IsInitiator))
    {
        // 0x73 PunchRetry 协调（现状，含台账失效退化全新 0x70 的 catch 口径）
        _scheduler.EnqueueRetry(session.PeerDeviceId);
    }
    // ② Failed 态周期重试（设计 12 §2.3 新增）
    foreach (var snap in _engine.Snapshots.Where(s => s.State == MappingState.Failed).ToList())
        _engine.RetryPunchAsync(snap.Config.MappingId);
}
```

### 5.4 触发点分类总表（Begin vs NextRetry）

| 触发点 | 位置 | 序列语义 | 出队协议 |
|---|---|---|---|
| 映射启用 | `MappingEngine.EnableAsync` → Enqueue | 新序列 | Begin=优先模式 |
| 手动重试 | `/api/mappings/retry` → `RetryAsync` → Enqueue | 新序列 | Begin |
| 隧道断链重入 | `OnTunnelDisconnected` → Enqueue | 新序列 | Begin |
| 控制通道重连补试 | `RetryFailedMappingsAsync` → `RetryAsync` | 新序列 | Begin |
| 中继回切 60s | `PunchRetryLoopAsync` ① → EnqueueRetry | 交替 | NextRetry |
| Failed 周期 60s（新） | `PunchRetryLoopAsync` ② → `RetryPunchAsync` → EnqueueRetry | 交替 | NextRetry |
| 被邀请方 B 侧 | 0x71/0x78 → `RespondAsync/RespondGoAsync`（不进队列） | —— | 由 invite 的 Tcp 槽位自动跟随 A |

> Begin 的重置语义：任一新序列触发（如用户手动重试）即重置该设备对交替计数——之后周期重试重新自优先模式开始交替。符合直觉："人工干预=从头再试"。
> 口径注记：表中"出队协议"经 §2.1 映射后为执行层口径（kcp→udp）传入 `Puncher.InitiateAsync`——0x70 proto / PunchOutcome.Proto / punch_stats 均落执行口径。

## 6. 打洞日志协议化（决策④）

### 6.1 PunchOutcome 加 Proto 尾字段

`PunchOutcome`（05 §3.1）尾部追加 `[property: ...] string? Proto = null`（**执行层口径 tcp/udp**，§2.1——与 0x70/punch_stats 对账一致；punchMode=kcp 的打洞记 `"udp"`）：

- A 侧：`InitiateTcpAsync/TryInitiateTcpLateAsync/InitiateTcpLegacyAsync` 路径填 `"tcp"`，`InitiateUdpAsync` 填 `"udp"`；
- B 侧：`RespondTcpAsync/RespondGoAsync` 填 `"tcp"`，`RespondUdpAsync` 填 `"udp"`；
- 中继回退产物（`FallbackToRelayAsync` 返回的 Ok 会话）：**继承本次打洞尝试的 proto**——日志语义为"本次用 X 协议打洞失败后回退中继"；
- `PunchOutcome.Failure(...)` 便捷构造追加可选参（既有调用点不填=null，仅旧测试形态；生产路径全填）。

### 6.2 日志口径（四型 + B 侧）

`PunchScheduler.LoopAsync` 四型日志（A 侧，运维主看线）统一加 `proto=`（取值=outcome.Proto，出队上下文同值兜底）：

```
[punch] 打洞成功 peer=3f2b… proto=tcp local=192.168.1.5:51000 peer=203.0.113.7:52000
[punch] 打洞失败 peer=3f2b… proto=udp：punch_timeout
[punch] 中继承载建立 peer=3f2b… proto=tcp relay=198.51.100.2:7020（打洞回退，02 §4.5）
[punch] 中继承载复用 peer=3f2b… proto=udp（回切重打失败，保持既有中继，M2-37）
```

B 侧：`ClientRuntime.HandleInviteAsync/HandleGoAsync` 在结果返回处补一条对齐口径的结果日志（现状无结果线日志；含 outcome.Proto 与 Ok/FailReason）：

```
[punch] 被邀请打洞完成 peer=… proto=tcp ok=True（0x71 会话）
```

- 0x72 上报（ClientReporter）**不带 proto**：服务端 punch_stats 的 proto 取自 0x70 台账（SignalingCoordinator 既有链路），本设计下自动正确，协议零改动。
- `[punch-tcp]` 计划线/收尾线（P4 诊断缝）保持现状，已自带前缀。

## 7. 隧道类型四态判别与展示（决策⑤）

### 7.1 TunnelSession.Bearer（四态，M6-08 三态判别扩展）

`TunnelSession` 既有判别 `ViaRelay`（`_transport is RelayTransport`）与 `RawUdpBearer`（`_transport is UdpPunchTransport`）同款风格，新增统一四态属性：

```csharp
/// 隧道承载形态（设计 12 §7）：relay=中继；kcp=UDP 直连 KCP 承载；raw-udp=UDP 直连裸承载；
/// tcp=TCP 直连（TcpFrameTransport 及兜底——TCP 直连为唯一剩余形态）。
public string Bearer => _transport switch
{
    RelayTransport      => "relay",
    KcpTunnelTransport  => "kcp",
    UdpPunchTransport   => "raw-udp",
    _                   => "tcp",
};
```

- `ClientReporter.BearerFor`（0x72 上报三态：KCP=1/裸=0/TCP·中继·失败=null，M6-08 决议）**逻辑不动**——上报口径与展示口径解耦，不因展示需求改变已批复的统计语义。

### 7.2 诊断端点与诊断页

- `TunnelView`（04 §2.6）尾部加 `string Bearer = "tcp"`；`GET /api/diagnostics/tunnels` 投影加 `s.Bearer`。
- 诊断页隧道表"承载"列（06 Settings 页）细化标签：`中继` / `直连·KCP` / `直连·UDP` / `直连·TCP`（现状"直连"二分为 UDP/TCP；tag 颜色中继=warning、直连系=success 不变；KCP tooltip 现状保留）。

### 7.3 设备发现页"隧道类型"列（06 §4）

- 数据源：复用 `GET /api/diagnostics/tunnels`（passive 亦可达，TunnelHost 本地表）——devices store 随 `refresh()` 并行拉取，构建 `Record<deviceId, bearer>`（tunnels 行的 peerDeviceId 与设备表 deviceId 同键直接关联）。
- 列呈现（"优先打洞模式"列之后，见 §8.3）：

| Bearer | 显示 | 样式 |
|---|---|---|
| relay | `中继` | el-tag warning |
| kcp | `直连·KCP` | el-tag success |
| raw-udp | `直连·UDP` | el-tag success |
| tcp | `直连·TCP` | el-tag success |
| 无隧道 | `—` | 纯文本 |

- 刷新口径：随设备页既有刷新动作（手动刷新按钮/WS device_list 事件驱动 refetch）拉取，不做隧道状态推送（映射状态变化已有 mapping_state WS 事件，设备页不订阅——保持轻量，运维点刷新即新）。
- raw-udp 第四态说明：用户可选模式只有 tcp/kcp（§2.1），但承载协商降级（对端 kill-switch 关/旧端混布）会真实产生裸 UDP 直连形态——列为第四态诚实展示"直连·UDP"，tooltip 注明"对端未启用 KCP，已降级裸 UDP"。
